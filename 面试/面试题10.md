# 一、Netty 网络编程（20 题）

### 1. Netty 是什么？谁在用？⭐⭐⭐

💡 一个**异步事件驱动的高性能网络应用框架**——帮你把 Java 网络编程里最难啃的 NIO 封装成人话 API 🎁。底层常客：**Dubbo / gRPC**（RPC 通信）、**RocketMQ**（消息网络层）、**Elasticsearch**（节点间通信）、**Spring WebFlux / Gateway**（默认服务器就是 Netty）、**Lettuce**（Redis 客户端）。

### 2. 为什么不直接用原生 NIO？⭐⭐⭐

💡 五个字：**难、坑、险、缺、慢**。① **API 复杂**（Selector/Channel/Buffer 手动配合容易写错）；② **臭名昭著的 epoll 空轮询 bug**（Selector 空转 CPU 100%）；③ 曾有 **UDP 漏洞**；④ **粘包拆包、心跳、重连全要自己造轮子**；⑤ Netty 全都解决了：高级封装 + 修复 bug + 开箱即用组件。

### 3. BIO / NIO / AIO 的区别？⭐⭐⭐

💡 **BIO 同步阻塞**：一连接一线程，accept 阻塞、read 阻塞、线程开销大（1 万连接 = 1 万线程爆炸💥）；**NIO 同步非阻塞**：Selector 多路复用，**少量线程管万级连接**，谁就绪处理谁；**AIO 真异步**：内核完成后回调通知（Linux 支持不成熟，实际用得少）。Netty 基于 **NIO** 封装。

### 4. 同步/异步、阻塞/非阻塞怎么区分？⭐⭐

💡 打饭类比🍚：**同步阻塞** = 站着干等；**同步非阻塞** = 取号后刷手机、时不时看叫号屏（还得自己问"好了吗"）；**异步** = 扫码点单，做好了小程序通知你，期间随便干啥。**NIO 属于同步非阻塞**——这是最容易被问懵的一点。

### 5. NIO 三大件是什么？⭐⭐

💡 **Channel 通道**（双向传输管道，比 Stream 单向强）、**Buffer 缓冲区**（数据读写都在这里，必走中转站📦）、**Selector 选择器**（盯着多个 Channel，只把"就绪"的交给你）。核心四事件：**OP\_ACCEPT / OP\_CONNECT / OP\_READ / OP\_WRITE**。

### 6. Buffer 的四个指针和 flip 是干嘛的？⭐⭐

💡 四指针：**capacity**（总容量不变）、**position**（当前读写位置）、**limit**（读写上限）、**mark**（书签，可 reset 回来）。写模式 `0 ≤ position ≤ limit ≤ capacity`；**flip()** = 把 position 归 0、limit 设为原 position——**写模式切换成读模式**，不 flip 就读不到数据。`clear()` 只是指针归零，**内容其实还在**。

### 7. select / poll / epoll 的区别？⭐⭐⭐

💡 都是 IO 多路复用，但代际明显：**select** fd 上限 **1024**、每次全量拷贝 + 线性扫描 O(n)；**poll** 用链表存 fd 无上限，但仍全量扫描 O(n)；**epoll** 用**红黑树注册 fd + 就绪链表回调**，只返回就绪的 O(1)，**海量连接下性能最优**（Linux 主流）。Netty 会按系统自动适配：Linux 用 epoll（还有专用 `EpollEventLoopGroup`）、Mac 用 kqueue、其他 select 兜底。

### 8. Netty 的线程模型？⭐⭐⭐（必考）

💡 **主从 Reactor 多线程模型**：`bossGroup`（MainReactor，**1 个线程**）只管 **accept 接客**，接到连接就注册给 worker；`workerGroup`（SubReactor，默认 **CPU 核数 × 2**）负责已连接 Channel 的**读写事件**。接客与干活分离，性能最优（Netty / Nginx / Memcached 同款）。另外两种：单 Reactor 单线程（一个慢操作卡全部，Redis 6.0 前）、单 Reactor 多线程（Reactor 单点）。

### 9. 为什么说 Netty 是"无锁串行化"？⭐⭐⭐

💡 关键在 **EventLoop = 一个线程 + 一个 Selector**，且**一个 Channel 终身只绑定一个 EventLoop**——同一个连接的所有事件都在同一个线程里**顺序处理**，天然不需要加锁，性能起飞🛫。这也是为什么**耗时业务必须移出 EventLoop 线程**（会卡住该线程上的所有连接）。

### 10. Netty 核心组件有哪些？⭐⭐

💡 **Bootstrap / ServerBootstrap**（启动引导器，组装一切）、**EventLoopGroup / EventLoop**（线程组与事件循环）、**Channel**（连接通道）、**ChannelPipeline**（处理器链，双向链表）、**ChannelHandler**（编解码与业务逻辑）、**ChannelHandlerContext**（上下文，链路传递）、**ByteBuf**（数据容器）、**ChannelFuture**（异步结果）。

### 11. Pipeline 的入站和出站方向？⭐⭐⭐

💡 Pipeline 是**双向链表**：**入站 Inbound**（数据进来：读、连接建立/断开）从 **Head → Tail**，典型是 Decoder 和业务 Handler；**出站 Outbound**（数据出去：写、bind/connect）从 **Tail → Head**，典型是 Encoder。习惯写法 `Decoder → Encoder → BusinessHandler`，顺序很重要。

### 12. ByteBuf 比 ByteBuffer 强在哪？⭐⭐

💡 ① **双指针 readerIndex / writerIndex**，读写互不干扰，**不用 flip**；② **自动扩容**；③ **池化**（PooledByteBufAllocator）减少 GC；④ 支持**堆外 Direct** 内存；⑤ **引用计数**管理堆外释放；⑥ 提供 **slice / duplicate / CompositeByteBuf** 等零拷贝操作。

### 13. ByteBuf 内存泄漏怎么防？⭐⭐

💡 坑在**堆外内存不受 GC 管理**，必须手动 release。规则：**谁最后引用谁释放**——入站读到 ByteBuf 自己消费了不往下传，必须 release；用 **SimpleChannelInboundHandler 会自动释放**（新手首选✅）。排查：`-Dio.netty.leakDetection.level=PARANOID` 开启泄漏检测，症状是堆外内存持续上涨直到 `OOM: direct memory`。

### 14. 什么是粘包拆包？怎么解决？⭐⭐⭐

💡 TCP 是**字节流，没有消息边界**——发三条消息可能被粘成一包（Nagle 合并、接收缓冲读取时机），也可能被拆成几段（MSS 分段）。**这不是 Bug，是 TCP 正常行为**；本质是应用层的"消息边界"丢了，要**自己在应用层定义边界**。四种解法：**定长**（FixedLengthFrameDecoder，浪费空间）、**特殊分隔符**（LineBasedFrameDecoder / DelimiterBasedFrameDecoder）、**长度域**（LengthFieldBasedFrameDecoder，**最通用、工业标准⭐**）、**自定义协议**（继承 ByteToMessageDecoder）。

### 15. LengthFieldBasedFrameDecoder 五个参数？⭐⭐⭐

💡 ① **maxFrameLength** 最大帧长度（防恶意大包）；② **lengthFieldOffset** 长度域偏移（跳过前面的协议头）；③ **lengthFieldLength** 长度域本身占几字节；④ **lengthAdjustment** 长度修正值（长度域的值与"后面还剩多少字节"的差值）；⑤ **initialBytesToStrip** 解析后丢弃前面几个字节。例：`[2字节头][4字节长度=N][N字节体]` → `(1MB, 2, 4, 0, 0)`。

### 16. 心跳怎么实现？⭐⭐

💡 用 **IdleStateHandler**（三个参数：readerIdleTime 读空闲 / writerIdleTime 写空闲 / allIdleTime 全空闲）+ 重写 **userEventTriggered**：**客户端**写空闲就自动发 PING；**服务端**读空闲累加计数，连续超阈值（如 3 次）判定僵尸连接直接 close🧟。目的：TCP 长连接被防火墙/NAT 悄悄掐断时，服务端能及时感知。

### 17. Netty 的零拷贝体现在哪？⭐⭐⭐

💡 **应用层三种**：① **CompositeByteBuf** 多个 ByteBuf 逻辑合并（拼协议头 + 包体）不复制；② **slice() / duplicate()** 共享底层数据的视图；③ **Unpooled.wrappedBuffer()** 包装 byte\[] 不复制。**操作系统层一种**：④ **FileRegion + transferTo()**（sendfile），文件从页缓存直达网卡**不经用户态**。⚠️ 注意区分：Netty 零拷贝指**避免程序内数据复制**，不等于 OS 的 mmap/sendfile 零拷贝。

### 18. epoll 空轮询 bug 是什么？Netty 怎么修？⭐⭐

💡 JDK NIO 在 Linux 上 `Selector.select()` 本该阻塞等事件，却可能**没事件也立即返回**→死循环空转→**CPU 100%💥。Netty 的修法：统计 select 空转次数，超过阈值（默认 512 次**）就新建一个 Selector 并把旧 Channel 迁移过去——神不知鬼不觉地"换个监听员"✅。

### 19. Handler 里业务太重怎么办？⭐⭐

💡 Handler 默认跑在 **EventLoop 线程**，耗时操作会卡住该线程上的**所有连接**。三种解法：① `ctx.channel().eventLoop().parent().execute(...)`（太绕）；② **自定义业务线程池 + handler 里提交任务**⭐；③ `pipeline.addLast(businessGroup, myHandler)`——**直接给这个 handler 指定线程组**（最优雅✅）。

### 20. Netty 和 Tomcat 的区别？⭐⭐

💡 **定位不同**：Tomcat 是 **HTTP(S) Web 容器**（Servlet 规范，面向 HTTP 应用）；Netty 是**通用网络框架**（自定义 TCP/UDP 协议、RPC、游戏服务器、中间件底层）。性能上 Netty 更轻量灵活；**Spring WebFlux 底层正是 Netty**。选型口诀：**写 Web 应用用 Tomcat，造协议/中间件用 Netty**。

# 二、Nacos 服务治理（16 题）

### 21. Nacos 是什么？名字怎么来的？⭐⭐

💡 **Na**ming and **Co**nfiguration **S**ervice → **Nacos**，官方定位"动态服务发现、配置管理和服务管理平台"。说人话：**服务的电话簿📖 + 配置的中央仓库🗄️**——一个组件顶 Eureka + Config 两个用。

### 22. Nacos 为什么受欢迎？⭐⭐

💡 ① **一站式**：注册中心 + 配置中心，不用拼装；② **可视化控制台**：点点鼠标改配置、下线服务；③ **AP/CP 可切换**：临时实例走 AP、持久实例走 CP；④ **性能好**：2.x 基于 gRPC 长连接，十万级服务也扛得住；⑤ 阿里出品，双十一海量流量验证💪。

### 23. Nacos 的数据模型有哪几层？⭐⭐⭐

💡 五层树🌳：**Namespace**（命名空间，环境/租户级隔离，dev 小区和 prod 小区互相看不见）→ **Group**（分组，默认 DEFAULT\_GROUP，像小区里的楼栋）→ **Service**（服务名，某户人家）→ **Cluster**（机房/区域，家里的不同房间，**同机房优先调用**）→ **Instance**（具体进程 `ip:port`）。最佳实践：**Namespace 隔离环境、Group 区分业务线、同机房同 Cluster**。

### 24. Namespace 最容易踩什么坑？⭐⭐

💡 **必须填 ID，不能填名称**！控制台创建时生成的那串 UUID 才是配置项要填的值。90% 的"服务注册不上/配置读不到"都是这个原因（另一个高频坑是**版本四件套没对齐**）。

### 25. 临时实例和持久实例的区别？⭐⭐⭐

💡 **临时实例**（默认，`ephemeral=true`）：客户端**心跳保活**，超时自动**剔除**；数据存**内存**，**Distro 协议 → AP**；适合微服务（挂了就删，干脆利落）。**持久实例**（`ephemeral=false`）：**服务端主动探测**健康，**不剔除只标记不健康**；数据存**磁盘/MySQL**，**Raft 协议 → CP**；适合 DB、Redis 这类基础组件（挂了也要留着记录排查）。

### 26. "Nacos 支持 AP 和 CP 切换"到底怎么切的？⭐⭐⭐

💡 **不是配置开关，而是按实例类型天然分流**：`ephemeral=true` → Distro 协议 → **AP**；`ephemeral=false` → Raft 协议 → **CP**。同理，**配置数据**走 Raft（CP）。一句话：**注册中心一般选 AP**——挂一小会儿没关系，但不能整个不可用。

### 27. Distro 协议的核心思想？⭐⭐⭐（面试加分）

💡 四点：① **全员可写**（每个节点都能接收写请求，保可用性）；② 每个服务的数据有一个**责任节点**，由它异步批量同步给别人；③ 新节点加入先**全量拉快照**再收增量；④ 临时实例数据存**内存**，节点重启丢了也没关系——**实例心跳很快会重新注册回来**🔄。本质：AP + 最终一致。

### 28. 服务发现为什么是"推拉结合"？⭐⭐⭐

💡 **推**：2.x 用 **gRPC 长连接实时推变更**（1.x 用 UDP，可能丢包）；**拉**：客户端**每 6 秒**定时全量拉取兜底，防推送丢失；再叠加**订阅**机制（Subscribe 感兴趣的服务）。最关键是消费者**本地缓存服务列表**——注册中心全挂了，调用照样能跑，这是**客户端缓存容灾**，也是 AP 思想的体现。

### 29. 保护阈值是什么？和 Eureka 自我保护有何不同？⭐⭐⭐

💡 场景：10 个实例挂 7 个，剩 3 个要干 10 份活 → 被打死 → 全挂。**保护阈值（protectThreshold）**：健康实例比例 < 阈值（如 0.5）时，**把不健康的实例也返回给调用方**——"死马当活马医，哪怕部分请求失败也捞回一些"。对比：**Eureka 自我保护**是**注册中心视角**（心跳大面积丢失时拒绝剔除，防误杀）；**Nacos 保护阈值**是**消费者视角**（健康实例太少时连不健康的也给你）——目的都是防雪崩。

### 30. 权重怎么用于灰度？有什么坑？⭐⭐

💡 实例 1 权重 0.9 接 90% 流量（老版本），实例 2 权重 0.1 接 10%（新版本金丝雀🐤）。⚠️ **大坑**：权重是 Nacos 元数据，但**默认的 RoundRobin 策略根本不读它**！想生效要自定义 LoadBalancer 策略（从 `NacosServiceInstance#getWeight` 取值），或用 Nacos 自带负载能力。

### 31. 优雅上下线怎么做？⭐⭐

💡 三种：① **主动注销** `NamingService#deregisterInstance()`（代码里 `registration.stop()`）；② **控制台下线**（实例还在跑，只是不给流量）；③ **权重调 0**——流量慢慢切走，**最平滑✅**（发布新版本的标准动作）。

### 32. 配置的"三元组"是什么？DataId 怎么命名？⭐⭐

💡 三元组 = **Namespace（哪个环境）+ Group（哪个分组）+ DataId（哪个文件）** = 唯一确定一份配置。DataId 规则：`${spring.application.name}-${profile}.${后缀}`，如 `order-service-dev.yaml`（dev 环境）、`order-service.yaml`（不带 profile = **通用配置，所有环境共享**）。

### 33. Boot 2.4+ 之后配置怎么拉？⭐⭐

💡 **不用 bootstrap.yml 了**（老教程的坑）！改用 **`spring.config.import`**：`- nacos:order-service.yaml` 和 `- nacos:order-service-${spring.profiles.active}.yaml`。**import 列表内越靠后优先级越高**（覆盖前面的）。排查"控制台能看到配置但客户端读不到"，先查三件事：DataId 拼写、namespace/group 是否一致、**config.import 写了没**。

### 34. @RefreshScope 刷新的原理是什么？⭐⭐⭐

💡 链路：收到配置变更 → 发布 **RefreshEvent** → Environment 里的值更新 → **销毁 @RefreshScope 标记的 Bean💥** → 下次请求进来时**重新创建 Bean**（用新值）。⚠️ 划重点：**不是改字段值，是整个 Bean 销毁重建**！所以 Bean 里的**缓存状态会被清空**，要小心。对比 **@ConfigurationProperties**：类型安全、集中管理、**自动热更新（不用加 @RefreshScope）**，推荐✅。

### 35. 2.x 只开 8848 为什么连不上？⭐⭐

💡 Nacos 2.x 改用 gRPC 长连接，**除了 8848（主端口/控制台）还必须开 9848**（= 8848 + 1000，客户端 gRPC 口），集群内部还有 **9849**（服务端间 gRPC）、**7848**（Raft 选举）。只开 8848 会报 `Client not connected, current status: STARTING`😱。Docker 部署记得 `-p 9848:9848`，云服务器安全组两个都要放行。

### 36. Nacos 集群怎么搭？生产注意什么？⭐⭐

💡 三步：① 每台 `conf/cluster.conf` 写全所有节点 `IP:port`；② **所有节点连同一个 MySQL**（集群必须外置 MySQL，内嵌 Derby 只适合单机）；③ 前面挂 **Nginx/VIP** 做负载均衡。注意：**节点数 3 个以上奇数**（Raft 要过半选举）；客户端 `server-addr` **填 Nginx 地址别写死某节点**；**开启鉴权** `nacos.core.auth.enabled=true` 并改默认密钥（默认密钥被曝过漏洞🙈）。客户端还有 **snapshot 本地快照**兜底，Server 挂了也能用旧配置。

# 三、Seata 分布式事务（15 题）

### 37. 为什么需要分布式事务？⭐⭐

💡 单体时代一个 `@Transactional` 搞定全部，因为**本地事务只能管自己库里的事**。拆成微服务后每个服务**各连各的库**：订单建好了、库存扣了、扣钱失败——**本地事务鞭长莫及**，数据直接不一致💥。跨库跨服务的"要么全成、要么全败"就需要分布式事务。

### 38. Seata 四种模式怎么选？⭐⭐⭐

💡 **AT**：短事务、无外部系统、想低侵入 → **绝大多数场景首选**🌟；**TCC**：性能敏感、不依赖 undo\_log、能改造业务表（要处理空回滚/幂等/悬挂）；**Saga**：**长流程、参与方多、含第三方系统**（别人家的库你没法加 undo\_log）；**XA**：**强一致刚需**（金融核心），能接受同步阻塞的性能损耗（切模式只需 `data-source-proxy-mode: XA` 一行配置）。

### 39. AT 模式怎么实现隔离？⭐⭐⭐

💡 靠 **全局锁**：AT 一阶段**本地事务已提交**，数据库行锁早就释放了，所以必须由 TC 维护一把绑定在"全局事务 + 行"上的锁——**全局事务改某行前必须先拿到该行全局锁**，拿不到就重试等待，保证两个全局事务不会交叉写同一行（**写隔离**，达到"全局读已提交"）。**读默认是读未提交**（性能优先），要强一致读用 `select ... for update`（会自动注册全局锁）。

### 40. 全局锁和数据库行锁的区别？⭐⭐

💡 **数据库行锁**：本地事务结束就释放；**Seata 全局锁**：绑定"全局事务 + 行"，从一阶段提交一直持有到**全局事务结束**（TC 记在 `lock_table`）。正因为 AT 一阶段就提交了本地事务、行锁已释放，才**必须靠全局锁防其他全局事务交叉写**。

### 41. undo\_log 回滚时为什么要校验后镜像？⭐⭐

💡 undo\_log 里存了 **beforeImage（改前）+ afterImage（改后）**。回滚时先校验 **当前数据 == afterImage**：相等（没人动过）→ 用前镜像生成反向 SQL 恢复✅；**不相等（被脏改了）→ 不能盲目覆盖，需要人工介入⚠️**。这就是"先验货再还原"，防止回滚把别人的正确数据抹掉。

### 42. TCC 的三大经典问题？⭐⭐⭐（必考）

💡 ① **空回滚**：Try 没执行（超时了），Cancel 却先到 → Cancel 白跑。解法：Cancel 先查**事务控制表**，没有 Try 记录 → 直接返回成功并记一条"空回滚"标记；② **幂等**：Confirm/Cancel 因重试执行多次 → 控制表记状态，**处理过直接返回**；③ **悬挂**：Cancel 先执行完，阻塞的 Try 这时才到 → 资源被冻结却永远没人管。解法：Try 执行前查控制表，**发现空回滚标记 → 拒绝执行🔒**。统一解药：\*\*事务控制表（xid + 分支状态）\*\*💊。

### 43. TCC 三阶段具体做什么（以扣库存为例）？⭐⭐

💡 **Try 预留资源**：`count=100, frozen=10`（冻结 10 个，别人不能用）；**Confirm 确认提交**：`count=90, frozen=0`（真正扣掉）；**Cancel 取消释放**：`count=100, frozen=0`（解冻还回去）。不由框架自动补偿，**三个方法全靠自己写**——控制力最强、性能最好，**侵入也最大**。注解：`@TwoPhaseBusinessAction(name, commitMethod, rollbackMethod)`。

### 44. Saga 模式适合什么场景？有什么缺点？⭐⭐

💡 适合**长流程、参与者多、含第三方系统**（别人的服务你改不了它的 SQL 加 undo\_log）。一阶段**直接提交本地事务**，失败就**逆序执行补偿**（没有"回滚"，只有"反向操作"），用**状态机 JSON 编排**（Seata 有可视化设计器）。最大缺点：**不保证隔离性**——中间状态别人看得见（比如订单已建、支付未完成）。

### 45. @GlobalTransactional 加了却不回滚，怎么排查？⭐⭐⭐

💡 四个元凶：① **注解加错地方**——必须加在**事务发起方（TM）**，XID 从那里开始；② **异常被 try-catch 吞了**（尤其 Feign 调用方吞掉，或远程服务内部自己 catch，TM 根本不知道失败）；③ **没配** **`rollbackFor = Exception.class`**（默认只回滚 RuntimeException）；④ XID 没透传（Feign 场景通常自动透传，自研 HTTP 调用要自己带）。

### 46. 报 `can not get global lock` 怎么办？⭐⭐

💡 全局锁竞争：① 两个全局事务抢同一行 → 后者重试，**默认重试 10 次 × 30ms**；② **非 Seata 事务**改了被全局锁保护的行。解法：**优化事务粒度**（别一个全局事务改太多表）、调整 `lock-retry-times`。

### 47. undo\_log 表里没数据是什么原因？⭐⭐

💡 三查：① **数据源代理没生效**（AT 靠代理 DataSource 拦截 SQL 才能生成 undo\_log）；② **表建错库**——`undo_log` 要在**每个业务库**建，不是建在 seata 库！③ **表名必须叫 undo\_log**，不能改。

### 48. TC Server 生产怎么高可用？⭐⭐

💡 TC 挂了所有全局事务都完蛋，所以要**集群**：① 存储用 **`store.mode=db`**（`file` 模式重启丢事务状态⚠️）；② TC 多节点注册到 **Nacos**，客户端从注册中心发现；③ **按机房分集群**（如 shenzhen/shanghai），`vgroup-mapping.my_tx_group: 集群名`——**同一事务组的服务连同一集群**；④ DB 存 `global_table / branch_table / lock_table`。

### 49. XID 是什么？怎么传播的？⭐⭐

💡 **全局事务的"身份证"**：TM 开启全局事务时 TC 返回，随调用链**跨服务透传**（HTTP 头 / MQ 消息），每个 RM 靠它知道自己属于哪个全局事务。Seata 已自动实现主流框架（Feign / RestTemplate / Dubbo / MQ）的透传，**自研通信方式要自己带上**。

### 50. @GlobalTransactional 和 @Transactional 能混用吗？⭐⭐

💡 **可以且推荐组合用**：`@GlobalTransactional`（全局）+ `@Transactional`（本地）。注意顺序：**全局注解在外层（发起方）**，**本地注解在各分支内部**。职责分工：RM 内部的本地事务保证该服务自己的原子性，TC 保证跨服务的全局一致性。

### 51. Seata 三大角色一句话记住？⭐⭐

💡 口诀：**TC 指挥、TM 发起、RM 干活、XID 串门、undo\_log 兜底**⚖️。TC = 独立部署的 Seata Server（事务协调者）；TM = 事务发起方（如订单服务）；RM = 每个参与方（订单/库存/账户）。

# 四、Skywalking 链路追踪（11 题）

### 52. 为什么需要链路追踪？⭐⭐

💡 微服务的"薛定谔故障"：用户说下单慢，你翻网关 → 订单 → 用户 → 库存 → 支付五个服务的日志，**半天过去了还没定位**😭。单体时代一个进程加个断点全知道，微服务一个请求穿越 5 台机器、日志散落各处——**链路追踪就是给微服务装 GPS + 行车记录仪**。

### 53. 可观测性三大支柱是什么？⭐⭐⭐

💡 **Logs 日志 / Metrics 指标 / Traces 链路**。一句话记：**日志看"点"（发生了什么离散事件）、指标看"面"（QPS/RT/错误率）、链路看"线"（请求走过的路径和每步耗时）**——三者合体就是可观测性（Observability）。代表工具：ELK/Loki、Prometheus、**SkyWalking⭐/Zipkin/Jaeger**。

### 54. Trace、Span、Segment 是什么关系？⭐⭐⭐

💡 **Trace** = 一次完整请求的全链路，全局唯一 **TraceId**（一张全程车票🎫）；**Span** = 链路里的**一步操作**（一次 RPC / DB / HTTP 调用，车票上盖的一个章📌）；**Segment** = **单个服务内的 Span 打包**（SkyWalking 特有，每个景点自己的游览记录）。Span 靠父子关系 + 上下文传播串成树。

### 55. TraceId 怎么跨服务传播？⭐⭐⭐

💡 **进程内**：方法传参 / ThreadLocal；**跨服务**：塞进**协议头**随 HTTP/RPC 飞过去——SkyWalking 用 **`sw8`** 头，下游 Agent 解析后**续上同一条链路**。所以接入时**网关也要挂 Agent**——头丢了链路就断了。跨服务追踪的本质是"每个环节都自觉传递上下文"。

### 56. SkyWalking 的架构组成？⭐⭐⭐

💡 四件套：\*\*Agent（探针）\*\*采集 → **OAP Server**（Observability Analysis Platform）收集 + 分析 + 聚合 → **Storage**（Elasticsearch / BanyanDB / H2）存历史数据 → **UI** 可视化（拓扑/链路/指标/告警）。一句话：**Agent 采 → OAP 算 → 存储放 → UI 看**。端口记牢：**11800 是 Agent 上报（gRPC）、12800 是 UI 查询**，别搞混。

### 57. Java Agent 无侵入的原理？⭐⭐⭐

💡 三步：① JVM 启动时通过 **`-javaagent`** 加载 `skywalking-agent.jar`；② 注册 **ClassFileTransformer** 拦截类加载；③ 用 **ByteBuddy 做字节码增强**，在 `OkHttp / JDBC / RedisTemplate` 等**中间件类的方法前后"织入"埋点**——方法一进一出 Span 就自动生成了🪄。所以业务代码**一行不改**也能有链路。

### 58. 接入时哪三个坑最容易踩？⭐⭐

💡 ① **`-javaagent`** **必须写在** **`-jar`** **前面**，放后面直接失效；② **网关也要挂 Agent**，否则链路不完整；③ **K8s 部署**要把参数写进 `Deployment.yaml` 的 **`JAVA_TOOL_OPTIONS`** 环境变量。另外 `service_name`（拓扑图上的名字）和 `backend_service`（OAP 的 gRPC 地址）两个参数必配。

### 59. 业务方法想被追踪怎么办？⭐⭐

💡 自动埋点只管中间件，业务方法加 **`@Trace`** 注解就成为一个 Span（还能 `operationName` 改名）。进阶：**`@Tags`** 打标签（`arg[0]` 取参数，查询时可按 tag 过滤）、**`ActiveSpan.tag(...)`** 记业务信息、**`ActiveSpan.error(...)`** 标记异常、**`TraceContext.traceId()`** 主动取 TraceId 返回前端做"精确制导"🎯。

### 60. 日志怎么和链路双向打通？⭐⭐

💡 引 **`apm-toolkit-logback-1.x`**，logback 里加 **`%tid`** 转换规则，日志就变成 `[TID:a1b2c3d4e5f6.78.1234] ...`。再加 **GRPCLogClientAppender** 把日志直接上报 SkyWalking——效果：**ELK 搜关键字拿到 TID → 去 SkyWalking 看完整链路；从链路点开 → 直接看该步日志**，排障效率起飞✈️。

### 61. SkyWalking 和 Zipkin 怎么选？⭐⭐

💡 **SkyWalking = APM 全家桶**（链路 + 指标 + 拓扑图 + 告警 + 日志 + Profile）且**无侵入 Agent、中文生态好**，国内 Java 微服务首选⭐；**Zipkin 轻量**、只做 Tracing，适合小项目。其他：Jaeger 云原生 Go 生态（K8s 多语言）、Pinpoint UI 炫酷。

### 62. 线上接口"偶发慢"怎么用 SkyWalking 排查？⭐⭐⭐

💡 **标准动线**：告警/用户反馈 → **Dashboard** 确认指标异常（RT P99? 错误率?）→ **Trace 按 URL 过滤**看慢链路瀑布图，红=慢/错 → **定位到最慢的 Span**（比如某条 SQL 280ms）→ 需要更细就 **Profile 方法级下钻**（CPU 时间切片采样，直达行号🔬）→ 结合 **日志(tid)** 佐证 → 修复上线。对比记忆：**Trace 是体检报告，Profile 是 CT 扫描**🩻。

# 五、Vert.x 异步编程（10 题）

### 63. Vert.x 是什么？和 Netty 什么关系？⭐⭐

💡 Eclipse 基金会出品的 **JVM 事件驱动、非阻塞异步工具包**（**Toolkit，不是框架**），底层引擎就是 **Netty**，在其上提供更高层抽象（Verticle / EventBus / Future / 全家桶），开发效率高一个量级。**能嵌进 Spring Boot 混用**（网关用 Vert.x、业务用 Spring 也行）。知名用户：**Quarkus 的底座**。

### 64. 传统 Tomcat 的线程模型痛在哪？⭐⭐

💡 **一请求一线程**，但线程大部分时间**在傻等 IO**（数据库 50ms、下游接口 200ms、Redis 5ms）——**线程很贵（内存 + 上下文切换）**，默认 200 线程，第 201 个请求就得排队。长连接（WebSocket）更惨：**一线程焊死一个连接**，万人在线 = 一万线程 = 直接爆炸💥。

### 65. Event Loop 是什么？黄金法则是什么？⭐⭐⭐

💡 **Event Loop 事件循环**：一条（默认 = **CPU 核数**条）**永不阻塞**的线程，循环干一件事——**从事件队列取事件 → 快速处理（微秒级）→ 取下一个**。**黄金法则：Never block the Event Loop！** Event Loop 上严禁 `Thread.sleep()`、同步 JDBC、耗时 for 循环、锁等待——**一个慢操作会卡住队列里所有事件，整条服务瘫痪**。Vert.x 有哨兵 BlockedThreadChecker 会大喊 `Thread blocked`。

### 66. Verticle 是什么？有哪几类？⭐⭐

💡 Verticle = Vert.x 的**部署单元**（一段部署到运行时的代码，类似微型 Actor）。**Standard Verticle** 跑在 **Event Loop**（绝大多数业务，IO 异步）；**Worker Verticle** 跑在**专用线程池**（不得不阻塞的任务：同步 JDBC、重计算）；还可**部署多实例并行**（`deploymentOptions.setInstances(4)`）。**业务状态别放 Verticle 字段**——多实例 + Event Loop 复用会互相污染。

### 67. EventBus 是什么？三种通信方式？⭐⭐⭐

💡 Verticle 之间**不直接调用**，通过 EventBus 异步收发消息（Vert.x 的神经系统📢）。三种：① **send 点对点**——多个消费者，**只有一个**收到（轮询挑一个）；② **publish 发布订阅**——**所有**订阅者都收到；③ **request 请求响应**——发消息并等回复（异步回调，返回 Future）。配 **Clustered EventBus**（Hazelcast/Infinispan）可**跨 JVM、跨机器**通信，就是分布式消息总线的味道🌉。

### 68. Future 和 Promise 的区别？⭐⭐⭐

💡 **Promise = 写入方**兑现/失败的凭证（后厨叫号器🔔），**Future = 读取方**等待结果的句柄（取餐小票🎫）；`promise.future()` 把关联的 Future 交出去。写异步方法的标准姿势：内部 `Promise.promise()`，异步完成后 `complete(x)` 或 `fail(err)`，返回 `promise.future()`。

### 69. 异步怎么避免"回调地狱"？⭐⭐⭐

💡 用 Future 链式组合：**`compose(fn)`** **串行**（上一步结果喂给下一步）、**`Future.all(f1, f2)`** **并行**（全成功才成功，`resultAt(i)` 取结果）、**`Future.any`** 任一成功即成功（竞速）、**`recover(fn)`** **失败兜底**（服务降级思想）、**`map(fn)`** 转换结果类型。对比：串行用 compose，并行用 all，兜底用 recover。

### 70. Event Loop 里必须写阻塞代码怎么办？⭐⭐⭐

💡 三种出路：① **`executeBlocking`**——临时借 Worker 线程池跑阻塞代码，**回调自动切回 Event Loop**（适合偶尔的阻塞）；② **Worker Verticle**——整块逻辑都阻塞（`setWorker(true)`，适合老系统桥接）；③ **原生异步客户端⭐**——`vertx-sql-client` / redis / mongo，**正解**（async 到底）。口诀：**能不阻塞就不阻塞，非阻塞不可就搬去 Worker，长期方案换异步客户端**。

### 71. Vert.x / Spring Boot / Netty 怎么选？⭐⭐

💡 **Spring Boot**：全家桶**框架**，一请求一线程（可异步），生态无敌，适合**业务管理系统**；**Vert.x**：事件驱动**工具包**，Event Loop 少量线程，**万人长连接轻松**😎，适合**高并发网关 / IM / IoT**；**Netty**：网络编程**底层框架**，极底层自己写协议，**自研中间件才碰**。选型口诀：**业务快糙猛选 Spring Boot，海量连接选 Vert.x，自研中间件才碰 Netty**。

### 72. Vert.x 靠什么做到高并发？常见坑有哪些？⭐⭐

💡 高并发四件套：**Netty NIO 多路复用** + **事件驱动回调（线程不等待 IO）** + **少量 Event Loop（省上下文切换）** + **异步客户端全家桶**。常见坑：`Thread blocked` 日志 = Event Loop 里写了阻塞代码；**Context 不是 ThreadLocal**——数据串了要用 `Vertx.currentContext().put()/get()`（不是 `ThreadLocal`）；异步太快导致**数据库连接池被打爆** → 设上限 + 限流；共享可变集合用 `SharedData` 并发容器。

# 六、WebSocket 实时通信（10 题）

### 73. 为什么需要 WebSocket？HTTP 卡在哪？⭐⭐

💡 HTTP 是**请求-响应**模型：**客户端不问，服务器打死不能说**🤐。可聊天、订单通知、行情推送、多人游戏这些场景偏偏需要服务器**主动推**。土办法都有缺陷：**短轮询**（每 2 秒白问一次）、**长轮询**（hold 30 秒但返回后要重连）、**SSE**（只能单向且仅文本）。

### 74. WebSocket 是什么？和 HTTP 的区别？⭐⭐⭐

💡 在**单个 TCP 连接**上做**全双工通信**的协议（RFC 6455），握手成功后双方**随时互发消息**、连接一直保持。对比 HTTP：**全双工 vs 一问一答**、**服务器可主动推**、**长连接 vs 短连接**、**帧头仅 2\~14 字节 vs 完整 HTTP 头几百字节**⚡、**文本 + 二进制都支持**。一句话：**HTTP 是传纸条，WebSocket 是打电话**☎️。

### 75. 握手过程是怎样的？⭐⭐⭐

💡 **蹭 HTTP 敲门再"过河拆桥"**：客户端发 `GET`，带 **`Upgrade: websocket`**、**`Connection: Upgrade`**、**`Sec-WebSocket-Key`**（随机串，防老式缓存代理乱入）；服务器回 **`101 Switching Protocols`**（换协议的标志性状态码⭐）+ **`Sec-WebSocket-Accept`**（用 Key + 固定魔法串做 SHA-1 算出，客户端校验合法性）；之后升级为 WS 双向通道。地址：`ws://` 明文 / **`wss://`** 加密（生产必备🔒）。

### 76. WebSocket 的数据帧和心跳机制？⭐⭐

💡 帧分三类：**文本帧**（字符串/JSON）、**二进制帧**（文件/图片/Protobuf）、**控制帧**（**Ping/Pong 心跳**、Close）；大消息自动**分片**。心跳存在的理由：TCP 长连接长时间没数据，可能被**路由器/防火墙/负载均衡悄悄掐掉**，所以每 **30\~60 秒**发 Ping，对方回 Pong 证明"我还活着"，配合 Nginx `proxy_read_timeout` 调大。

### 77. @ServerEndpoint 的四大注解？有什么大坑？⭐⭐⭐

💡 四注解：**@OnOpen**（接通电话📞）、**@OnMessage**（对方说话🗣️）、**@OnClose**（挂断👋）、**@OnError**（串线掉线😵）。**大坑**：`@ServerEndpoint` 类**每个连接都会 new 一个新实例**！所以会话池必须 **`static`** **+ 并发安全容器**（ConcurrentHashMap），不然广播就失效；另外\*\*`@Autowired` 会注入为 null\*\*（脱离 Spring 管理），需手动取 Bean 或改用 Spring Handler 方式。

### 78. Spring 的 Handler 方式为什么更推荐？⭐⭐

💡 原生注解和 Spring 生态（拦截器、依赖注入 Service）整合不好。**生产推荐** **`TextWebSocketHandler`** + `@EnableWebSocket` 注册端点：`afterConnectionEstablished` 上线、`handleTextMessage` 收消息、`afterConnectionClosed` 下线。点对点私聊维护 `userSessionMap`（key = userId），用 **`HandshakeInterceptor`** 握手前校验 token 并把用户信息塞进 `attributes`。

### 79. 集群部署时消息推不到，为什么？⭐⭐⭐（最大生产坑）

💡 **Session 不跨 JVM**！小明连在实例 A，运维"给小明推消息"的请求被 Nginx 打到实例 B——**B 内存里根本没有小明的 Session，消息石沉大海**😢。三种解法：① **粘性会话**（IP hash 固定实例，简单但实例挂了 Session 全丢）；② **Redis Pub/Sub 广播**⭐（主流）——推消息先发到 Redis 频道，**所有实例都收到**，各自检查"这个用户在不在这"；③ **MQ 广播**（RabbitMQ/Kafka，大规模可持久化）。

### 80. Nginx 反代 WebSocket 必配哪两行？⭐⭐⭐

💡 口诀：**"一 map 二 set 头，timeout 拉长久"**。必须 `proxy_http_version 1.1` + **`proxy_set_header Upgrade $http_upgrade`** + **`proxy_set_header Connection $connection_upgrade`**（配 map 把 `$http_upgrade` 映射成 upgrade/close），再把 **`proxy_read_timeout`** **调大**（默认 60s 会掐线）。**两个头不透传，握手必失败**，浏览器报 `failed: Error during WebSocket handshake`。

### 81. 断线了怎么自动重连？⭐⭐

💡 前端 `onclose` 触发**指数退避重连**：`1s → 2s → 4s → 8s ...` 上限 30s，**防止服务器崩溃时被重连请求打爆**；重连成功再**重新订阅 / 补拉离线消息**。配合前端定时心跳（30s 发一次 ping 帧）判断连接是否还活着。

### 82. STOMP 是干嘛的？什么时候用？⭐⭐

💡 裸 WebSocket 只是一根"水管"，消息格式全靠自己约定；**STOMP 在水管上定义 SEND/SUBSCRIBE/MESSAGE 指令**，像订阅频道一样用。Spring 支持超好：`@EnableWebSocketMessageBroker` + `enableSimpleBroker("/topic","/queue")` + `@MessageMapping("/chat")` + `@SendTo("/topic/messages")`。适合**聊天室分频道、点对点投递、和 RabbitMQ 等真消息代理打通**；简单推送用裸 WebSocket 就够。
