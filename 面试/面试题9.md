# 一、SpringCloud 总览与服务治理（15 题）

### 1. 单体架构有哪些痛点？⭐⭐⭐
💡 ① **改一处全量重启**（改个 logo 也要重新部署整个系统）；② **技术锁死**（全 Java 写的，想换语言没门）；③ **一崩全崩**（订单模块 OOM → 整站挂掉）；④ **发布慢**（几百人协作一个工程互相踩脚）。

### 2. 微服务的核心特征？⭐⭐⭐
💡 按**业务**拆成一个个独立小服务：**独立进程、独立部署、独立数据库**，通过 HTTP/RPC 互相调用——一句话：**独立崩溃互不拖累**！但拆完冒出新烦恼（互相怎么找到？请求发给谁？配置怎么管？雪崩怎么防？），SpringCloud 全家桶就是来解决这些的。

### 3. SpringBoot 和 SpringCloud 什么关系？⭐⭐⭐
💡 **Boot 专注个体**：快速开发单个应用的脚手架（做一块乐高积木🧱）；**Cloud 治理全局**：注册、调用、熔断、网关等服务治理生态（把积木拼成城堡🏰）。**Cloud 必须基于 Boot**，Boot 可以独立存在。

### 4. SpringCloud 自己生产组件吗？⭐⭐
💡 **不生产，只是优秀开源组件的搬运工 + 包装工**📦：把成熟的第三方组件（Nacos / Gateway / Sentinel…）包装成统一的 Spring 风格开发体验（注解、自动装配、starter），屏蔽底层差异。

### 5. Netflix 组件为什么被抛弃？现在的黄金组合是？⭐⭐⭐
💡 Eureka、Ribbon、Hystrix、Zuul、Feign 全家桶陆续**停止维护**（只修 bug 不加新功能）。当下黄金组合🏆：**Nacos**（注册+配置中心）+ **OpenFeign**（服务调用）+ **Gateway**（网关）+ **LoadBalancer**（负载均衡）+ **Sentinel**（熔断限流）+ **Seata**（分布式事务）。

### 6. 注册中心的工作原理？⭐⭐⭐
💡 本质是微服务的**电话簿**📞：① **注册**——服务启动把地址注册上去；② **发现**——消费者拉取服务列表并**缓存到本地**；③ **心跳**——服务每 **5s** 续约，**15s** 没收到标记不健康，**30s** 还没收到直接剔除下线。

### 7. Nacos / Eureka / Zookeeper / Consul 怎么选？⭐⭐⭐
💡 看 **CAP**：**Nacos** 默认 AP、可切 CP（还自带配置中心，一站式首选✅）；**Eureka** 纯 AP（自我保护宁滥勿缺）；**Zookeeper / Consul** 走 CP（保证一致但选举期间不可用）。业务注册中心一般**选 AP**——可用比强一致更重要，列表旧一点没事，拿不到列表全完。

### 8. Eureka 自我保护机制是什么？⭐⭐⭐
💡 短时间内**心跳大量丢失**（多半是网络抖动不是真挂）时，Eureka **宁可信服务还活着也不删除注册信息**——因为大面积误删会让所有消费者拿不到列表，引发调用雪崩。AP 的极致体现：**宁可数据陈旧，也要保证可用**。

### 9. CAP 和 BASE 理论？⭐⭐⭐
💡 **CAP**：一致性 C / 可用性 A / 分区容错性 P，三选二——但 **P 是分布式必选**（网络分区一定会发生），实际是 CP 与 AP 之争；**BASE** 是 AP 的补丁理论：**基本可用 + 软状态 + 最终一致**（大促降级、订单"支付中"状态、数据延迟几百毫秒追平）。

### 10. 配置中心解决什么问题？⭐⭐
💡 100 台机器改配置文件改到吐，改完还要挨个重启？配置中心**统一管理 + 热更新**：配置放 Nacos，改完**秒级推送**到所有实例，不用重启。

### 11. Nacos Config 热更新的两种姿势？⭐⭐⭐
💡 ① **@Value + @RefreshScope**：配置变更时刷新 Bean 重新注入；② **@ConfigurationProperties**：绑定的属性**自动刷新**（推荐）。⚠️ @RefreshScope 的 Bean 会被代理，使用时留意。

### 12. Seata AT 模式的两阶段原理？⭐⭐⭐
💡 核心是**一阶段就本地提交**，锁持有时间最短！① 一阶段：解析业务 SQL 记录**前后镜像**存进 **undo_log**，**本地事务直接提交**释放本地锁，向 TC 注册分支；② 二阶段：**全局提交** → 异步删 undo_log（几乎零成本）；**全局回滚** → 按 undo_log **反向补偿**恢复数据。对业务**无侵入**，加个注解就能用。

### 13. @GlobalTransactional 是干嘛的？TM/TC/RM 三角色？⭐⭐⭐
💡 加在**事务发起方**方法上开启全局事务，生成全局事务 id（XID）随调用链传播。**TM**（事务发起方）管开局与裁决提交/回滚；**TC**（独立部署的 Seata 服务端）管全局协调；**RM**（每个参与方）管分支事务执行与上报。

### 14. 分布式事务方案怎么选（2PC/AT/TCC/Saga/消息最终一致）？⭐⭐⭐
💡 **2PC**：同步阻塞、协调者单点，性能差；**AT**：无侵入、自动补偿，最常用（有不一致窗口）；**TCC**：Try-Confirm-Cancel 手写三段，**侵入大但性能好**，核心资金场景；**Saga**：长事务正向执行 + 逆向补偿，适合跨系统长流程；**消息最终一致**：本地消息表 + MQ 异步，吞吐最高，能容忍延迟的场景。

### 15. 链路追踪是什么？Sleuth 为什么换 Micrometer Tracing？⭐⭐
💡 微服务一调用十几个服务，出 bug 不知道请求走到哪——链路追踪给每个请求发身份证：**TraceId**（一次全链路请求唯一）+ **SpanId**（单次调用），配合 **Zipkin** 收集展示调用链路与耗时。Sleuth 停更后由官方 **Micrometer Tracing** 接棒（Boot 3.x 标配），概念基本平移。

# 二、Gateway 网关（15 题）

### 16. 为什么需要网关？⭐⭐⭐
💡 没有网关：内网 IP 裸奔🩳、鉴权代码复制 N 遍、每个服务配一遍 CORS、流量进来像脱缰野马🐎。网关 = 微服务的**大门保安 + 前台小姐姐**：所有请求先过它——**查证件（鉴权）、指路（路由）、控制人流（限流）、记登记（日志）、管跨域（CORS）**。

### 17. 三大核心概念 Route / Predicate / Filter？⭐⭐⭐
💡 **Route**：一条转发规则的完整打包（断言 + 过滤器 + 目标 URI），像一条快递线路📦；**Predicate**：断言请求符不符合条件（路径/方法/请求头…），符合才"接单"🔍；**Filter**：转发前（pre）/ 响应返回前（post）加工处理（改请求头/鉴权/限流）🛂。

### 18. 请求在 Gateway 里的执行流程？⭐⭐⭐
💡 Netty 接收 → **DispatcherHandler** 分发 → **RoutePredicateHandlerMapping** 遍历所有路由的断言找第一个匹配的（没匹配 404）→ **FilteringWebHandler** 把该路由的 GatewayFilter + 全部 GlobalFilter **按 order 排序**组装过滤器链 → **pre 前置处理**（鉴权/改头/限流）→ **NettyRoutingFilter**（链上最后的执行者）真正转发 → 目标服务响应 → **post 后置处理**返回。pre 正序 post 逆序，**洋葱模型**🧅。

### 19. 为什么网关工程不能引 spring-boot-starter-web？⭐⭐⭐
💡 Gateway 基于 **WebFlux + Reactor + Netty** 的**响应式非阻塞**模型；starter-web 是 **SpringMVC + Tomcat** 阻塞式——两者默认服务器一个 Netty 一个 Tomcat，混在一起**启动直接报错**🙅。

### 20. Gateway 比 Zuul 1.x 强在哪？⭐⭐⭐
💡 Zuul 1.x 基于 **Servlet 阻塞**，每请求占一个线程；Gateway 基于 **WebFlux + Netty 非阻塞**，少量 EventLoop 线程处理海量请求——性能更优秀、原生支持长连接/WebSocket，且官方持续更新（Zuul 停更💤）。

### 21. Gateway 和 Nginx 什么关系？⭐⭐
💡 不是替代，是**情侣档**💑：**Nginx 管最外层**——通用流量入口（静态资源、四层/七层负载）；**Gateway 管里面**——微服务业务网关（lb:// 与注册中心无缝集成、Java 写 Filter 丝滑）。口诀：**Nginx 管大门，Gateway 管室内**。

### 22. lb:// 是什么意思？503 是怎么回事？⭐⭐⭐
💡 `lb://order-service` = 去注册中心找该服务的实例列表 + **负载均衡**选一个转发。⚠️ **必须引入 loadbalancer 依赖**，没有它网关做不了负载均衡，直接 **503**！

### 23. 常用断言有哪些？⭐⭐
💡 11 种内置：**Path**（路径匹配，最常用⭐）、Method、Host、Header、Query、Cookie、**After/Before/Between**（时间窗口——大促路由只在活动期生效🎉）、RemoteAddr、**Weight**（按权重分流：同组 90% 走 v1、10% 走 v2，**灰度发布神器**🐤）。断言全部满足才匹配，多条匹配按 order 小的优先。

### 24. 内置过滤器哪些常用？⭐⭐
💡 **StripPrefix**（去掉路径前 N 段，`/api/product/1` → 1 段 → `/product/1`）、**PrefixPath**（加前缀，反向操作）、**RewritePath**（正则重写）、**AddRequestHeader / AddRequestParameter**（塞请求头/参数）、**SetStatus**（改响应码）、**Retry**（重试）、**RequestRateLimiter**（限流）、**CircuitBreaker**（熔断）。

### 25. GatewayFilter 和 GlobalFilter 的区别？⭐⭐⭐
💡 **GatewayFilter**：只作用于**某一条路由**（yml 里 filters 配的）；**GlobalFilter**：作用于**所有路由**（@Component 实现 GlobalFilter 接口即生效）。鉴权这种全局的事当然用 GlobalFilter～

### 26. 全局鉴权过滤器怎么写？⭐⭐⭐
💡 实现 **GlobalFilter + Ordered**：① 白名单路径（登录/注册）直接放行；② 取 token 校验（通常查 Redis）；③ 解析出用户 id，**塞进请求头 X-User-Id 透传给下游**（下游不用再解一遍 token）；④ 不通过 setStatusCode(401) 写回。order 要够小，保证在转发前执行。

### 27. 动态路由怎么实现？⭐⭐
💡 两种：① `discovery.locator.enabled: true`——**自动按服务名发现**路由，新服务上线零配置；② 把路由配置放 **Nacos**，监听配置变更后**触发 RefreshRoutesEvent 热刷新**路由表——不重启网关就能改路由。

### 28. RequestRateLimiter 是怎么限流的？⭐⭐⭐
💡 底层是 **Redis 令牌桶**（Lua 脚本保证原子）：**KeyResolver** 决定限流维度（按 IP / 按用户 / 按接口——返回的 key 不同就分开限）；**replenishRate** = 每秒补充令牌数（平均速率），**burstCapacity** = 桶容量（允许的突发量）。

### 29. CORS 跨域在哪里配？⭐⭐
💡 **统一在网关配，下游服务别再配**！两边都配会返回重复的 CORS 响应头，浏览器直接报错。网关用 `spring.cloud.gateway.globalcors` 统一配 allowedOriginPatterns / allowedMethods。

### 30. 网关常见 404 怎么排查？⭐⭐
💡 大多是**断言不匹配**（Path 写错）或 StripPrefix 层数不对。排查：开 `logging.level.org.springframework.cloud.gateway=debug`，能看到每个请求匹配了哪条路由。另外记得透传 **X-Forwarded-For**，不然下游拿到的全是网关 IP 不是真实客户端 IP。

# 三、LoadBalancer 负载均衡（9 题）

### 31. 负载均衡是什么？解决什么问题？⭐⭐⭐
💡 把请求**雨露均沾**地分摊到多个服务实例上，换来三样东西：**吞吐量**（多机合力）、**可用性**（一台挂了其它顶上）、**扩展性**（加机器就加容量）。微服务多实例部署的刚需。

### 32. 服务端 LB 和客户端 LB 的区别？⭐⭐⭐
💡 **服务端 LB**（Nginx / LVS / F5）：独立部署的中间层**集中转发**，请求要多跳一跳到 LB 再到服务；**客户端 LB**（Spring Cloud LoadBalancer）：负载均衡逻辑**在自己进程内**，从注册中心拉服务列表**直连**目标实例，少一跳更快。⚠️ 客户端 LB **必须依赖注册中心**（不然列表从哪来）。实际架构两者互补：Nginx 管大门，LoadBalancer 管室内。

### 33. 常见负载均衡算法有哪些？⭐⭐⭐
💡 **轮询**（挨个来）、**加权轮询**（机器好的多分点）、**随机 / 加权随机**、**最少连接**（谁手头活少给谁，适合长耗时请求）、**源 IP 哈希**（同一 IP 固定打同一台，**会话保持**）、**一致性哈希**（普通哈希加一台机器全乱、一致性哈希**增减机器只影响相邻段**）、最小响应时间（谁快给谁）。

### 34. Ribbon 为什么退役？LoadBalancer 接了什么班？⭐⭐⭐
💡 Ribbon 是 Netflix 家的，2020 年进入**维护模式**（退役💤）。Spring Cloud LoadBalancer 是**官方亲儿子**：更轻量、服务列表用 **Caffeine 缓存**。⚠️ SC 2020.0 之后 **OpenFeign 不再自带 Ribbon**，必须**显式引入 loadbalancer 依赖**——老项目升级最容易踩的坑。

### 35. @LoadBalanced 的原理？⭐⭐⭐
💡 本质是给 RestTemplate **塞一个 LoadBalancerInterceptor 拦截器**：发请求时拦下来，把 URL 里的**服务名**（`http://order-service/api`）**翻译**成真实 `IP:端口`（从注册中心拉列表 + 负载均衡算法选一个）再发出去。忘加 @LoadBalanced 会 UnknownHostException——真把服务名当域名去解析了。

### 36. LoadBalancer 的三种使用姿势？⭐⭐
💡 ① **@LoadBalanced RestTemplate**：显式声明式调用；② **OpenFeign**：无感使用（底层自动集成）；③ **LoadBalancerClient.choose("服务名")**：手动选实例自己发请求（最灵活）。

### 37. 默认策略是什么？怎么换成随机？⭐⭐
💡 默认**轮询**（RoundRobinLoadBalancer）。想换随机：写配置类注册 **RandomLoadBalancer**，通过 `@FeignClient(configuration = xxx.class)` 挂到指定客户端——⚠️ 这个配置类**千万别放在主容器能扫到的包**（要的就是单独生效于这个客户端，被扫到就全局生效覆盖所有服务了）。

### 38. 服务列表缓存在哪里？多久更新？⭐⭐
💡 拉回来的实例列表放在 **Caffeine 缓存**里，默认 **35 秒**过期，到期重新去注册中心拉——所以实例下线后，消费方最多有几十秒的"旧名单"延迟。

### 39. 常见报错怎么破？⭐⭐
💡 **No LoadBalancer for xxx**：没引 loadbalancer 依赖；**No instances available**：服务没注册上或被剔除（先查 Nacos）；**UnknownHostException**：忘加 @LoadBalanced，服务名没被翻译。老项目还要小心 Ribbon 残留依赖打架。

# 四、OpenFeign 服务调用（12 题）

### 40. OpenFeign 是什么？"声明式"什么意思？⭐⭐⭐
💡 **声明式 HTTP 客户端**：只要写个**接口 + 注解**（@FeignClient + SpringMVC 注解），框架帮你生成实现——**像调本地方法一样发 HTTP 请求**，感知不到 HTTP 细节。Feign 是 Netflix 的（停更💤），OpenFeign 是社区接力的版本。

### 41. OpenFeign 的工作原理？（高频）⭐⭐⭐
💡 五步走：① **@EnableFeignClients** 扫描 @FeignClient 接口；② 用 **JDK 动态代理**为每个接口生成 Bean 注册进容器；③ 调用方法时代理拦截，**解析注解**（URL/参数/请求头）构建 HTTP 请求；④ 通过 **LoadBalancer** 把服务名换成真实实例（负载均衡选一个）；⑤ 发请求，**解码器**把响应反序列化成返回类型。

### 42. 日志有哪四级？为什么配了不输出？⭐⭐⭐
💡 **NONE**（默认啥也不打）/ **BASIC**（方法 URL 状态码耗时）/ **HEADERS**（+请求响应头）/ **FULL**（+请求体响应体，排查神器）。⚠️ 光配 Logger.Level 还不够，必须把接口所在包的日志级别调成 **debug**（yml 的 logging.level）才输出。

### 43. 超时怎么配？谁覆盖谁？⭐⭐⭐
💡 分**全局**（default）和**局部**（按服务名单独配），**局部优先级高于全局**。Boot 3.x 前缀是 `spring.cloud.openfeign.client.config.服务名.connectTimeout / readTimeout`。默认连接 10s、读取 60s，生产必须调小！

### 44. 默认会重试吗？⭐⭐⭐
💡 **默认 NEVER_RETRY 不重试**（防重复下单这种事故，默认值设计得很稳）。要开就自定义 **Retryer**（如 maxAttempts=3），但**只对幂等请求**（查询类）开——非幂等接口重试 = 重复下单现场🚨。

### 45. GET 请求传对象为什么会变 POST 报 405？⭐⭐⭐
💡 大坑⚠️：GET 接口的参数是**对象**且没加注解，Feign 会把对象当请求体序列化——**偷偷变成 POST**，服务端只认 GET 直接 405。解法：参数上加 **@SpringQueryMap**，把对象映射成查询参数（?a=1&b=2）。

### 46. 服务间的 token / 用户身份怎么透传？⭐⭐⭐
💡 网关校验完塞请求头（X-User-Id）透传下游；而服务间 Feign 调用传 token：写 **RequestInterceptor**，从 **RequestContextHolder** 取当前请求的 Authorization 头塞进 **RequestTemplate**——每个 Feign 请求自动带上。⚠️ 异步线程里 RequestContextHolder 拿不到（ThreadLocal 隔离），要装饰线程池传递上下文。

### 47. fallback 和 fallbackFactory 的区别？⭐⭐⭐
💡 都是 Feign 整合熔断时的兜底：**fallback** 写法简单但**拿不到异常信息**（不知道为啥失败）；**fallbackFactory** 的方法能拿到 **Throwable**，可以打日志定位问题——**生产推荐 fallbackFactory**。

### 48. Feign 接口的最佳工程实践（API 模块）？⭐⭐
💡 把接口抽到**公共 API 模块**：Provider **implements** API 接口（路径天然一致，不会两边 URL 写岔），Consumer 引依赖注入直接调。⚠️ Provider 的启动类**不要开 @EnableFeignClients**（它不当消费者）。

### 49. 文件上传怎么搞？⭐⭐
💡 接口 consumes 声明 **MULTIPART_FORM_DATA** + 参数用 @RequestPart + 配置 **SpringFormEncoder**（默认编码器不认 multipart）。

### 50. Feign 性能可以怎么优化？⭐⭐
💡 ① 底层 HTTP 客户端**换 OkHttp / Apache HttpClient**（连接池复用，默认不连池每次新建）；② 配置合理的**超时与重试**；③ 日志生产环境关掉（FULL 很耗性能，只联调开）；④ 大对象传输考虑压缩。

### 51. 常见坑有哪些？⭐⭐
💡 ① **contextId 冲突**：同服务多个 @FeignClient 不指定 contextId 启动报错；② **参数忘写 value**：@RequestParam 不写值且编译没开 -parameters，运行期参数名丢失；③ **fallback 不生效**：没开熔断开关（Sentinel 场景要 `feign.sentinel.enabled: true`，通用是 circuitbreaker.enabled）。

# 五、Sentinel 流量防护（14 题）

### 52. Sentinel 是什么？能干嘛？⭐⭐⭐
💡 阿里开源的**面向分布式服务架构的流量防护组件**，以流量为切入点：**流量控制、熔断降级、热点防护、系统自适应保护**——微服务的"保险丝 + 保安队长"，让系统稳如老狗🐶。

### 53. 什么是雪崩效应？根因是什么？⭐⭐⭐
💡 根因是**同步调用 + 线程阻塞等待**：下游服务卡死 → 请求堆积不返回 → 上游线程被占满 → 层层向上拖垮 → **整条链路全崩**❄️💥。单个服务的小病，演变成全站瘫痪。

### 54. 限流、熔断、降级分别是什么？⭐⭐⭐
💡 口诀记牢：**限流保自己**（入口防御，流量太大就拒绝多余的——景区限流🎫）；**熔断保链路**（下游坏了就跳闸快速失败不再真调，给下游喘息——家里跳闸⚡）；**降级保体验**（失败了返回兜底数据优雅善后——外卖没了吃泡面🍜）。

### 55. Sentinel 和 Hystrix 的区别？（必考）⭐⭐⭐
💡 ① 隔离策略：Hystrix **线程池隔离**（隔得干净但线程开销大），Sentinel **信号量隔离**（直接限并发线程数，轻量高效）；② 熔断策略：Sentinel 有**慢调用比例 / 异常比例 / 异常数**三种，Hystrix 仅异常比例；③ 规则修改：Sentinel **控制台动态推送即时生效**，Hystrix 改代码重启；④ Sentinel 独有**流量整形**（Warm Up 预热 / 排队等待削峰）、**热点参数限流**、**系统自适应保护**；⑤ Hystrix 停更💤，Sentinel 持续活跃✅。

### 56. Sentinel 的两大核心概念？五大规则？⭐⭐
💡 **资源**（被保护的东西：一个方法/接口——景区的景点🏞️）+ **规则**（怎么保护——景区的管理规章📋），资源是中心、规则围着资源转。五大规则：**流控**（流量大小）、**熔断**（故障隔离）、**热点**（特定参数值精准打击）、**系统**（整体水位）、**授权**（来源黑白名单）。

### 57. Sentinel 的底层原理？（源码加分）⭐⭐⭐
💡 **Slot 责任链**，像机场安检一道道关卡✈️：**NodeSelectorSlot**（构建调用树）→ **ClusterBuilderSlot**（构建统计节点）→ **StatisticSlot**（**滑动窗口**实时统计 QPS / RT / 线程数）→ **Authority / System / Flow / Degrade** 各 Slot 依次检查规则 → 违规抛 **BlockException**。一句话总结：**滑动窗口做统计、责任链做检查、异常做信号**。

### 58. 滑动窗口比固定窗口好在哪？⭐⭐⭐
💡 固定窗口在**边界会被打穿**：限 100/s，第 1 秒末来 100 个 + 第 2 秒初来 100 个，任意 1 秒窗口都没超，但瞬间真实流量 200。滑动窗口把窗口切成小格子**滚动统计**，任意时刻往前看都是完整窗口——**平滑无死角**，这就是 Sentinel 实时统计的底座。

### 59. 流控阈值类型 QPS 和并发线程数怎么选？⭐⭐⭐
💡 **QPS** 限每秒请求数（保护吞吐，常用）；**并发线程数**限同时执行的线程数——**慢接口用它更精准**：RT 2 秒的接口 QPS=10 时，实际可能同时 20 个线程在跑，"别占我这么多线程"的诉求只有线程数阈值贴合。

### 60. 流控的三种模式？⭐⭐⭐
💡 **直接**（默认）：自己到阈值限自己；**关联**：**关联资源**到阈值时限**自己**——经典场景：**下单（写）压力大时限流查询（读），保写不保读**🤯；**链路**：只统计从某条入口链路进来的流量（同一资源多个入口只限其一），⚠️ 要配 `web-context-unify: false` 关闭链路收敛才生效。

### 61. 流控的三种效果？⭐⭐⭐
💡 **快速失败**（默认）：超阈值直接拒——排队人太多不让进❌；**Warm Up 预热**：从 **阈值/3** 开始慢慢爬升到阈值——秒杀开始时缓存冷、连接池没热，直接放满会被秒杀流量压垮，先放 1/3 缓一缓🌡️；**排队等待**：**漏桶匀速**放行，等超时才拒——**突发流量削峰填谷**，消息处理 / 异步任务神器🎫。

### 62. 熔断的三种策略和状态机？⭐⭐⭐
💡 策略：**慢调用比例**（RT 超过"最大 RT"的请求占比超标，适合下游变慢）、**异常比例**（适合偶发出错）、**异常数**（绝对次数，适合低流量接口——比例不准时用绝对数）。状态机：**Closed**（闭合正常放行🟢）→ 统计指标超阈值 → **Open**（打开熔断，请求快速失败**不再真调**，给下游喘息🔴）→ 熔断时长结束 → **HalfOpen**（放一个探测请求🟡）→ 成功恢复 Closed，失败继续 Open。

### 63. 热点参数限流是什么？有什么注意点？⭐⭐⭐
💡 普通限流**一刀切**，热点限流**按参数值精准打击**🎯：参数索引 0 + 单机阈值 5——顶流商品 id=666 被刷爆时单独限它，其它商品照常跑。还有**参数例外项**：id=666 单独给阈值 50（顶流多给点额度）。⚠️ 两个坑：① 只对 **@SentinelResource** 定义的资源生效（URL 资源配热点规则不生效）；② 参数必须是**基本类型或 String**（对象没法统计）。

### 64. blockHandler 和 fallback 的区别？⭐⭐⭐
💡 **blockHandler** 接 **Sentinel 规则违规**（BlockException：限流/熔断触发时走它，返回"人太多啦稍后再试"）；**fallback** 接 **业务异常**（Throwable：代码抛 NPE 走它）。签名：都和原方法**同参数同返回值**，blockHandler 末尾多一个 BlockException 参数；两者可同时配、各管各的。另外默认被限流返回 "Blocked by Sentinel" 纯文本——可实现 **BlockExceptionHandler** 返回统一 JSON。

### 65. 规则持久化怎么做？⭐⭐⭐
💡 默认规则存**内存**，**重启全丢**❌。方案：① **Pull 拉模式**：写本地文件数据源定时轮询，有延迟；② **Push 推模式（生产标准✅）**：规则存 **Nacos**，服务引 `sentinel-datasource-nacos` + 配 `rule-type` 监听，改 Nacos **秒级生效**。⚠️ Dashboard 默认把规则推到内存，想"控制台改的规则直接进 Nacos"需要改造 Dashboard 源码。
