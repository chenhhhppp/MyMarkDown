# 一、MySQL（23 题）

### 1. 数据库设计的三范式？⭐⭐⭐
💡 **1NF** 字段原子不可再分；**2NF** 非主键字段完全依赖主键（消除部分依赖）；**3NF** 非主键字段不依赖其他非主键（消除传递依赖）。实战常**反范式**：适度冗余字段换查询性能，别死守范式。

### 2. SQL 语句的书写顺序和执行顺序？⭐⭐⭐
💡 书写 `SELECT...FROM...WHERE...GROUP BY...HAVING...ORDER BY...LIMIT`；执行 **FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT**——SELECT 几乎最后才执行，所以 **WHERE 里不能用 SELECT 起的别名**，ORDER BY 可以。

### 3. DATE / DATETIME / TIMESTAMP 怎么选？⭐⭐
💡 DATE 纯日期（3 字节）；DATETIME 日期+时间（8 字节，存什么是什么，**不受时区影响**）；TIMESTAMP 时间戳（4 字节，**自动做时区转换**）。要跨时区/自动更新用 TIMESTAMP，一般记录时间用 DATETIME。

### 4. utf8 和 utf8mb4 的区别？⭐⭐
💡 MySQL 的 utf8 是**残血版**（最多 3 字节，存不了 emoji 表情）；**utf8mb4** 才是真 UTF-8（4 字节）。建库建表连接串无脑 utf8mb4，不然用户昵称带个 🎉 就报错。

### 5. NULL 有哪些坑？⭐⭐⭐
💡 ① `= NULL` 永远查不到，必须 **IS NULL**；② COUNT(字段) **忽略 NULL**；③ **NOT IN** 子查询里有 NULL 整个结果为空；④ NULL 参与运算结果还是 NULL。建议：字段尽量 **NOT NULL + DEFAULT**。

### 6. UNION 和 UNION ALL 的区别？⭐⭐⭐
💡 UNION **去重**（要多一步排序合并，慢）；UNION ALL **不去重**（直接拼接，快）。确定无重复或不在乎重复，用 ALL 省性能；两表列数、顺序、类型要对应。

### 7. 子查询有哪些种类？⭐⭐
💡 按结果：**标量子查询**（单值，可当常量用在 SELECT/WHERE）、**列子查询**（配 IN）、**行子查询**、**表子查询**（FROM 后或 EXISTS）；按是否引用外层：**相关子查询**（逐行执行，慢）vs **不相关子查询**（执行一次）。

### 8. 自连接是什么？什么场景用？⭐
💡 一张表**当两张用**，必须起别名区分——经典场景：员工表里有 `manager_id` 指向同表的领导，查「员工姓名 + 领导姓名」就靠自连接。

### 9. INSERT 遇到主键/唯一键冲突怎么办？⭐⭐
💡 三招：**INSERT IGNORE**（静默跳过）；**REPLACE INTO**（删旧插新，有触发 DELETE 的副作用）；**ON DUPLICATE KEY UPDATE**（冲突就原地更新指定字段，最常用）。

### 10. 为什么推荐自增整型主键，不用 UUID？⭐⭐⭐
💡 聚簇索引数据**按主键物理有序**：自增 ID 永远**顺序追加**到最后一页，写满换页即可；UUID 乱序插入 → 频繁**页分裂**产生碎片，且 36 字符占空间大、范围查询无意义。分布式下用雪花 ID（趋势递增）。

### 11. 唯一索引和普通索引怎么选？⭐⭐
💡 **业务上要防重复**（手机号、订单号）必须唯一索引——数据库层兜底比代码判断靠谱；纯粹为了查询加速选普通索引。查询性能两者几乎一样。

### 12. 什么是前缀索引？⭐⭐
💡 长字符串（url、email）只取**前 n 个字符**建索引，省空间；n 用**区分度**（不重复值/总数）挑到接近全列即可；代价：无法做覆盖索引和 ORDER BY。

### 13. 索引是不是越多越好？⭐⭐⭐
💡 不是：① 每个索引一棵 B+ 树**占磁盘空间**；② 增删改要**维护所有索引树**，写入变慢；③ 索引多了优化器**选择成本上升**还可能选错。原则：只给查询常用、区分度高的列建，冗余索引定期清理。

### 14. ORDER BY 为什么会出现 filesort？怎么优化？⭐⭐⭐
💡 排序列**没被索引覆盖**（或联合索引顺序断了、方向混用），MySQL 只能把结果拉到内存/磁盘排序。优化：给 WHERE + ORDER BY 的列建**联合索引**且满足最左前缀连续命中，让排序顺着索引走，EXPLAIN 里 Extra 不再出现 `Using filesort`。

### 15. 大表 COUNT(*) 很慢怎么办？⭐⭐
💡 InnoDB 因 MVCC 每个事务看到的行数不同，没法像 MyISAM 直接存个数，只能扫。方案：**单独计数表**（增删改时同步维护）、**Redis 计数**、允许近似值用 EXPLAIN 的 rows 估算。

### 16. 乐观锁和悲观锁的区别？⭐⭐⭐
💡 **乐观锁**：假设没冲突，加 **version 字段**，`UPDATE ... SET version=version+1 WHERE id=? AND version=?`，影响行数为 0 就重试——适合**读多写少**；**悲观锁**：假设必冲突，`SELECT ... FOR UPDATE` 先锁住再改——适合**写多冲突高**。

### 17. 死锁是怎么产生的？怎么避免？⭐⭐⭐
💡 两个事务互相持有对方想要的锁，循环等待。InnoDB 会**死锁检测**自动回滚代价小的事务。避免：① 多个资源**按相同顺序**访问；② 事务尽量小、尽快提交；③ WHERE 列有索引（锁行不锁全表扫描范围）；④ 必要时降低隔离级别。

### 18. binlog / redo log / undo log 三大日志各干嘛？⭐⭐⭐
💡 **undo log**：记旧版本，用于**回滚 + MVCC**（原子性）；**redo log**：InnoDB 引擎层物理日志，WAL 先写日志保证崩溃恢复（持久性）；**binlog**：Server 层逻辑日志，用于**主从复制和数据恢复**。前两个在引擎层，binlog 属于 MySQL 整体。

### 19. 主从复制延迟怎么办？⭐⭐⭐
💡 主写从异步同步，延迟必然存在。解法：① **写后立即读**的关键操作强制走主库；② 写主后短时间内（如 1s）该用户请求都路由主库；③ 半同步复制（至少一个从收到才返回）；④ 并行复制提速能力。

### 20. 什么时候才分库分表？垂直和水平怎么分？⭐⭐⭐
💡 经验值：单表数据量过大（**千万级**、索引树过高、SQL 明显变慢）或单库磁盘/QPS 到瓶颈才做。**垂直**：按业务拆库、按冷热/大字段拆表；**水平**：按分片键（用户 id）把行拆到多库多表。代价巨大（分布式事务、跨库 JOIN、分布式 ID、扩容迁移）——**能不做就不做**，先索引、缓存、读写分离、归档。

### 21. 一条慢 SQL 的排查思路？⭐⭐⭐
💡 ① 开**慢查询日志**定位到具体 SQL；② **EXPLAIN** 看 type（有没有全表扫）、key（走没走索引）、rows（扫了多少行）、Extra；③ 优化三板斧：**加/改索引**（考虑最左前缀、覆盖索引）→ **改写 SQL**（避免失效写法、深分页、select *）→ **架构层**（冗余字段、归档、读写分离）。

### 22. 视图（VIEW）是什么？适合干什么？⭐⭐
💡 一条 SELECT 的**虚表**——只存定义不存数据，查视图时执行底层查询。用途：**简化复杂查询**（多表 join 封装成一张"表"）、**权限隔离**（只暴露部分列给某些人）。注意：视图不会让查询变快。

### 23. 长事务有什么危害？⭐⭐
💡 ① 锁长期不释放，**阻塞别人**；② undo log 无法清理，**膨胀**；③ MVCC 旧版本链拉长，**普通查询也变慢**；④ 加剧主从延迟。监控 `information_schema.innodb_trx`，发现跑得久的事务及时 kill。

# 二、Redis（15 题）

### 24. Redis 和 Memcached 的区别？⭐⭐
💡 Redis 胜在：**数据类型丰富**（5 基础 + 3 特殊 vs 纯 KV）、**支持持久化**（RDB/AOF）、**高可用**（主从/哨兵/集群）、value 上限 512MB（Memcached 1MB）；Memcached 多线程、纯内存缓存够快。现在基本无脑 Redis。

### 25. SDS 比 C 字符串好在哪？⭐⭐
💡 ① len 字段记录长度，取长度 **O(1)**（C 要遍历到 \0）；② **二进制安全**（不以 \0 判断结尾，能存图片、序列化对象）；③ **空间预分配 + 惰性释放**，减少频繁 realloc。

### 26. ZSet 为什么用跳表不用红黑树？⭐⭐⭐
💡 跳表 = 多层链表，从高层往下跳，平均 O(logN)。选它三个理由：① **范围查询天然支持**（ZRANGE 顺着底层链表扫，红黑树要中序遍历回溯）；② **实现简单**（插入删除改指针，红黑树旋转变色彩难写难调）；③ 内存可调（层高按概率生成，不是严格平衡）。

### 27. 布隆过滤器的原理？⭐⭐⭐
💡 **bit 数组 + k 个哈希函数**：写入时把 key 哈希 k 次置 k 个位为 1；查询时 k 个位**全 1 →「可能存在」**（可能误判），**有 0 →「一定不存在」**（绝不漏判）；**不支持删除**（一个位可能被多个 key 共用）。经典用途：缓存穿透拦截、爬虫 URL 去重。

### 28. pipeline 是什么？和事务区别？⭐⭐
💡 把多条命令**打包一次网络往返**发过去，省的是 RTT（网络来回）。注意：**不是原子操作**——只是批量发送，命令仍逐条执行，中途某条失败后面的照跑。

### 29. Redis 事务里的 WATCH 是干嘛的？⭐⭐
💡 乐观锁（CAS 思想）：`WATCH key` 后再 MULTI/EXEC，**EXEC 时检查 key 是否被别人改过**，改过则整个事务放弃执行返回 nil，客户端自行重试。

### 30. AOF 文件越来越大怎么办？⭐⭐
💡 **AOF 重写**：fork 子进程根据**当前内存状态**生成一份等价的最小命令集（一个 key 被写 100 次只留最终值），写入新 AOF 后替换；重写期间新命令写重放缓冲，最后追加。文件瞬间瘦身，且不阻塞主线程。

### 31. 什么是大 key 问题？⭐⭐⭐
💡 value 过大（String 几百 KB、集合几十万元素）。危害：**读写慢阻塞单线程**、网络拥塞、**删除卡顿**（同步 DEL 也阻塞）、主从同步慢、集群数据倾斜。排查：`redis-cli --bigkeys`。解决：**拆分**（大 hash 分桶）、压缩存储、删除用 **UNLINK**（异步）。

### 32. 什么是热点 key 问题？⭐⭐
💡 某个 key 访问特别集中（爆款商品），流量全砸在一个分片/一台机器上打满它。解决：① **本地缓存**兜底（Caffeine 挡第一层）；② key **打散多副本**（key_1~key_N 随机读一个）；③ 读写分离、多从扛读。

### 33. 缓存预热和缓存降级是什么？⭐⭐
💡 **预热**：上线/重启**之前**把热点数据提前加载进缓存，防止冷启动瞬间全部 miss 打垮 DB；**降级**：Redis 真挂了的保命手段——限流 + 返回默认值/本地的旧数据，牺牲体验保系统不崩。

### 34. 哨兵模式和集群模式怎么选？⭐⭐
💡 **哨兵** = 主从 + 自动故障转移：只解决**高可用**，容量和写吞吐仍限单机；**集群** = 16384 槽分片：**容量 + 写扩展 + 高可用**一体。数据量单机装得下、只是怕挂 → 哨兵；数据大/写多要横向扩 → 集群。

### 35. 用 Redis 怎么做接口限流？⭐⭐⭐
💡 三种：① **固定窗口**：`INCR + EXPIRE` 计数（简单，但窗口临界有突刺）；② **滑动窗口**：ZSet 存请求时间戳，`ZREMRANGEBYSCORE` 清窗口外 + `ZCARD` 数当前窗口；③ **令牌桶**：Lua 脚本原子补令牌（允许突发流量）。

### 36. Redis 怎么做秒杀防超卖？⭐⭐⭐
💡 库存放 Redis，**Lua 脚本原子**完成「判断库存 → 扣减 → 记录该用户」三步，让竞争在 Redis 单线程里排队；DB 层再加 `WHERE stock > 0` 兜底；配合前端按钮置灰、MQ 削峰。核心思想：**把数据库的行锁竞争前移到内存里串行化**。

### 37. 延时队列怎么用 ZSet 实现？⭐⭐
💡 member = 任务 id，score = **到期时间戳**；消费者轮询 `ZRANGEBYSCORE key 0 now` 拿到期任务，再 `ZREM` 抢占——**删成功才算自己的**（防多消费者重复执行）。适合订单超时关闭等场景；可靠性要求高就换 MQ 延迟消息。

### 38. 点赞功能怎么设计？⭐⭐
💡 量小：**Set**（`SADD like:post:1 uid` 去重、SISMEMBER 判断、SCARD 计数）；量大：**Bitmap**（`SETBIT like:post:1 uid 1`，BITCOUNT 计数超省空间）；最终异步批量落 DB 做持久化。

# 三、ElasticSearch（8 题）

### 39. 相关度评分 _score 是怎么算的？⭐⭐
💡 ES 5+ 默认 **BM25**（TF-IDF 改进版）：**词频饱和**（出现 10 次不比 5 次强多少）、**文档长度归一**（长文档词天然多，适当降权）、**IDF**（越稀有的词权重越高）——所以搜「苹果手机」时两个词都命中的文档排更前。

### 40. ES 默认分词器对中文有什么问题？⭐⭐
💡 standard 把中文**逐字切开**（「数据库」→ 数/据/库），搜「数据」全是单字匹配，语义全无、相关性一塌糊涂 → 必须装 **IK 分词器**按真实词语切分。

### 41. mapping 定错了还能改吗？⭐⭐
💡 **已有字段的类型改不了**（倒排索引已生成无法逆转），只能 **reindex** 建新索引迁移数据；**新增字段**可以随时加。优雅姿势：用**别名 alias** 对外提供索引名，重建完把别名一切换，业务零停机。

### 42. 集群健康状态 green / yellow / red 是什么意思？⭐⭐⭐
💡 **green**：主分片 + 副本全部就位（健康）；**yellow**：主分片都在，**副本没分配**（如单节点放不下副本，数据暂时单份）；**red**：**有主分片丢失**，数据不完整——最危险，立刻处理。

### 43. ES 深分页为什么危险？怎么解决？⭐⭐⭐
💡 `from + size` 时每个分片都要取 `from+size` 条回协调节点汇总排序，页越深越爆内存，所以默认**上限 10000**。方案：**search_after**（用上一页最后一条的排序值当游标，只能顺序翻，实时翻页首选）、**scroll**（拉快照批量导出用，不适合实时）。

### 44. MySQL 的数据怎么同步到 ES？⭐⭐⭐
💡 三方案：① **同步双写**：代码里写完 MySQL 再写 ES（简单但耦合、部分失败难处理）；② **MQ 异步**：写 MySQL 发消息，消费者刷 ES（主流，解耦削峰）；③ **binlog 订阅**：Canal 监听 binlog 刷 ES（**对业务零侵入**，最终一致）。

### 45. ES 的搜索高亮是怎么实现的？⭐
💡 请求加 `highlight` 指定字段，ES 把命中的词前后包上 `<em></em>` 标签，返回 highlight 片段，前端把标签渲染成黄色底——「关键词飘黄」就是这么来的。

### 46. ES 支持事务吗？⭐⭐
💡 **不支持 ACID 事务**：分布式架构 + 近实时 refresh + 跨文档无法回滚，天生**最终一致**的读侧。所以定位是**搜索引擎**不是主存储——强一致数据老老实实放 MySQL，ES 只负责搜。

# 四、MongoDB（6 题）

### 47. BSON 和 JSON 的区别？⭐⭐
💡 BSON 是**二进制**的 JSON：带**长度前缀**可快速跳过不需要的字段、类型更丰富（Date/ObjectId/Int64/Decimal/二进制）、无需文本解析所以**序列化更快**——MongoDB 存取快的原因之一。

### 48. ObjectId 是怎么组成的？⭐
💡 12 字节 = **4 字节时间戳 + 5 字节机器/进程随机标识 + 3 字节自增计数器**：天然含时间**大致按创建顺序排**、分布式下不冲突、不需要中心节点发号。

### 49. 嵌套文档和引用（类似内嵌 vs 外键）怎么选？⭐⭐⭐
💡 **一起读的、一对少量、有界的** → 嵌入（一条文档全拿到，还天生原子）；**多对多、无限增长的、被多方引用的** → 引用（$lookup 或应用层查两次）。口诀：**读优先就嵌入，长得快就拆出去**——这也是 MongoDB「靠设计规避事务」哲学的核心。

### 50. Read Preference 是什么？⭐⭐
💡 **读路由策略**（对应写的 Write Concern）：`primary`（默认，读主强一致）、`secondary`（读从，分担压力但最终一致）、`primaryPreferred / secondaryPreferred / nearest`（各种兜底）。报表、Feed 流这类**容忍旧读**的用 secondary，交易类用 primary。

### 51. MySQL 也有 JSON 类型了，为什么还要 MongoDB？⭐⭐⭐
💡 MySQL 的 JSON 本质是**文本存储**：建索引要靠虚拟列、无 schema 校验、聚合能力弱、难水平扩展；MongoDB 是** BSON 文档原生**：任意字段直接建索引、聚合管道、分片原生支持。偶尔存个扩展字段用 MySQL JSON 没问题；**文档就是主体**的业务（内容、日志、行为流）还是 MongoDB。

### 52. 什么时候才需要给 MongoDB 上分片？⭐⭐
💡 单机副本集**磁盘装不下、内存扛不住、写入到瓶颈**时才上。演进顺序：先纵向升级机器 → 副本集扩读 → 都不行再分片。分片带来路由复杂度 + 跨分片查询限制，而且**分片键几乎不能改**——能晚上的就晚点上。

# 五、综合实战（4 题）

### 53. 高并发计数器（文章阅读量）怎么设计？⭐⭐⭐
💡 别每次 read 都 UPDATE MySQL：**Redis INCR** 原子扛并发 → **攒批/定时**（如每 5 秒或每 +100）把增量异步批量落库；容忍最终一致即可。Redis 重启丢失就定时用 DB 值校准兜底。

### 54. 连续签到统计怎么设计？⭐⭐
💡 **Bitmap** 按月一个 key（`sign:uid:202610`）：签到 `SETBIT 天-1 1`、当月总签到 `BITCOUNT`；**连续签到**：从今天往前逐位与（位运算），连续 1 的个数就是天数；补签就是补 SETBIT——365 天才 46 字节，极致省空间。

### 55. 排行榜出现同分并列怎么办？⭐⭐
💡 ZSet 同分默认按 **member 字典序**排（不公平）。技巧：**score 拼接辅助值**——`score = 分数 × 10¹³ + (MAX_TS - 达成时间戳)`，先比分数再比「先到先得」；member 只存业务 id，展示时按新 score 排即可。

### 56. 四件套分别「不能干什么」？⭐⭐⭐
💡 反向记牢不踩坑：**MySQL** 别硬扛海量模糊搜索（LIKE 全表扫）和超高并发读；**Redis** 别当主数据库（内存贵、持久化非绝对可靠）；**ES** 别当强一致主存储（无事务 + 近实时 1 秒丢写窗口）；**MongoDB** 别依赖跨文档强事务（性能代价大）——每个都是好刀，但别用刀背炒菜～
