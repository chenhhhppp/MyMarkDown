# 一、CI/CD 持续集成与交付（12 题）

### 1. CI / 持续交付 / 持续部署 三者怎么分？⭐⭐⭐
💡 **CI（持续集成）**：代码一 push 就**自动编译 + 测试**，保证"代码是好的"；**CD 持续交付**：测试过了**自动打包成制品**，停在"发版按钮"前等你点（**有一道人工闸门🟡**）；**CD 持续部署**：全自动一路发到生产，人都不用点。口诀：**CI 保代码，交付保管制品，部署保一路发🚀**。

### 2. 完整流水线必经哪几关？⭐⭐
💡 七步：**拉代码 → 编译构建 → 自动化测试 → 质量门禁（SonarQube 覆盖率/漏洞）→ 打包镜像 → 推送镜像仓库（Harbor/Nexus）→ 部署测试 + 冒烟验收**，最后到生产时"持续交付"等人点、"持续部署"自动推。

### 3. Jenkins / GitLab CI / GitHub Actions 怎么选？⭐⭐
💡 **GitLab CI**（已用 GitLab 自建的团队首选，`.gitlab-ci.yml` 与仓库天然一体）；**GitHub Actions**（开源项目 / GitHub 用户，市场现成 Action 一堆）；**Jenkins**（遗留系统多、流程奇葩需要自定义，插件生态海量但也最臃肿🤯）；云原生全 K8s 场景常组合：**Jenkins/GitLab CI 出镜像 + ArgoCD 部署**。

### 4. 三种部署策略：滚动 / 蓝绿 / 金丝雀 怎么挑？⭐⭐⭐
💡 **滚动发布**（K8s 默认）：新旧交替逐个换，**几乎无停机、资源成本低**，大多数场景默认✅；**蓝绿部署**：两套完整环境一键切换，**秒回滚⚡但双倍成本**（只给核心业务、回滚要极致快）；**金丝雀发布🐤**：先放 5% 流量试水，指标正常再放量，**影响面最小但发布慢**。口诀：**通用用滚动、核心用蓝绿、风险大用金丝雀**。

### 5. 金丝雀发布名字由来？核心逻辑？⭐⭐
💡 以前矿工下井带金丝雀探毒气（鸟没事人才敢进）🐤。核心逻辑：**先把 5%~10% 流量引到新版本**，盯着错误率、耗时、QPS；指标正常则逐步放量 → 20% → 50% → 100%；指标异常立即撤回 0%，影响面**被锁定在小范围**。

### 6. GitOps vs 传统 CD 的核心差别？⭐⭐⭐
💡 本质是**谁当指挥官**：**传统 CD** = CI 脚本直接 `kubectl apply` 改集群（集群真实状态是"真相"，漂移了就没人管了🔄）；**GitOps** = CI **只改 Git 仓库里的镜像版本号**，ArgoCD 监听 Git 变化自动同步，**Git 仓库是唯一真相📜** → 回滚 = `git revert` 一条命令，审计 = 每次变更是一次 Git commit，漂移自动纠正。

### 7. GitOps 的完整工作流怎么走一遍？⭐⭐
💡 五步：① 业务代码 push → CI 编译测试 → ② 打镜像推 Harbor → ③ **CI 自动 PR 改"部署仓库"里 K8s YAML 的镜像版本号** → ④ ArgoCD 监听到 Git 变化 → ⑤ 对比 Git 期望 vs 集群实际 → **自动 Sync 更新 K8s 集群**。CI 管造包、GitOps 管上包，Git 是唯一指挥官。

### 8. 流水线反模式有哪些？⭐⭐
💡 六大坑：① **一个流水线编译 N 次**（各环境包不一致、又慢）；② **镜像用 `latest` 标签**（出事不知道线上是哪版😱）；③ **密码明文写 YAML**（走 Jenkins credentials / GitLab Variables 加密存🔐）；④ **绕过流水线手动 `kubectl`**（GitOps 漂移越改越乱）；⑤ **没有回滚预案**（出事干瞪眼）；⑥ **没配质量门禁**（坏代码混进主干）。

### 9. 为什么镜像标签必须带版本号、禁用 latest？⭐⭐⭐
💡 `latest` **不代表"最新"**——它只是"没指定 tag 时自动给的默认名"，可能指向任何版本。生产上 5 台机器拉 `latest` 结果各自拉到不同时间点的不同镜像 → **不可复现、问题不可追溯**🚨。版本标签用**构建号 + commit SHA**（如 `1.2.0-42-ab12cd3`），出事能精准定位到哪次代码。

### 10. "一次构建、多处部署"到底什么意思？⭐⭐
💡 同一个**带版本号的镜像**（比如 `order-service:v1.3.2`）**走过 test → staging → prod 所有环境**，而不是每个环境重新 `docker build` 一次。好处：各环境行为 100% 一致、出问题能复现、审计链路清晰。

### 11. 多阶段构建是什么？Java 场景怎么用？⭐⭐⭐
💡 **在 Dockerfile 里用 `AS builder` 语法分多个 `FROM`**，前一段用来编译（带 Maven/JDK 大工具链），后一段只拷编译产物进精简运行时。Java 经典两阶段：`FROM maven:3.9 AS builder` 打 jar → `FROM eclipse-temurin:17-jre-alpine` 只拷 jar。单阶段 ~800MB，多阶段 **~200MB**，瘦身 75%✨。

### 12. 构建缓存原则是什么？怎么利用？⭐⭐
💡 **"变得少的写前面，变得勤的写后面"**——因为 Docker 构建时，**从上往下某层没变就直接跳过用缓存**。Java 场景：**先 COPY pom.xml → `mvn dependency:go-offline` 下依赖**（依赖几乎不变 → 这层被缓存），再 COPY src 源码（天天变 → 只重编译这一层）。反例：一上来 `COPY . .` → 每次改一行代码依赖全重下💔。

# 二、DDD 领域驱动设计（12 题）

### 13. DDD 一句话定义 + 核心思想？⭐⭐⭐
💡 **让代码围绕"业务"来设计，而不是围绕"数据库表"来设计**🎯。四大核心：**通用语言**（业务代码说同一套话）、**业务驱动**（业务边界 = 代码边界）、**分而治之**（大系统切成小王国）、**模型沉淀**（业务规则沉淀在领域模型里而不是散落 if-else）。Eric Evans 2003 年提出。

### 14. 贫血模型 vs 充血模型 差在哪？⭐⭐⭐
💡 **贫血模型**（传统三层的 Service + 一堆 DTO）：实体只有 getter/setter，**业务逻辑全堆 Service** → Service 越长越肥、魔法字符串满天飞、规则改一处牵一片💣；**充血模型**（DDD 的实体/值对象）：**业务行为写进领域对象里**——`Order.cancel()` 自己检查状态，绕不过去（聚合根强制保证）。口诀：**贫血 = Service 扛全部，充血 = 领域对象自己守家**。

### 15. 核心域 / 支撑域 / 通用域 怎么分、投入策略？⭐⭐⭐
💡 **核心域🌟**：赚钱的看家本领、和竞争对手拉开差距的地方（如电商的智能定价/推荐算法）→ **投最优秀的人 + 最多资源**；**支撑域🔧**：必须有但不是竞争力（订单管理、售后工单）→ 够用就好；**通用域📦**：大家都一样（登录认证、邮件通知）→ **直接买成熟方案、别自己造轮子**🦋。

### 16. 通用语言（Ubiquitous Language）到底是什么？⭐⭐⭐
💡 **让所有人（产品/开发/测试/运维）都说同一套业务词汇，并且这些词汇直接出现在代码里**。反例：产品说"核销"，代码写 `updateStatus(3)`、类名 `TbOrderInfoDTO` → 新同学看代码像猜哑谜🤡。正例：`order.writeOff()`、类名 `Order` → **看代码 = 看需求文档**。

### 17. 限界上下文 ≠ 子域？一句话分清！⭐⭐⭐
💡 **子域**是**业务问题**的划分（问题空间，如"商品/订单/库存"）；**限界上下文**是**软件方案**的划分（解决方案空间）。理想情况一个子域对应一个上下文，但现实常有一对多。关键结论：**同一个词在不同限界上下文里含义可以完全不一样**——经典例子"商品"在商品上下文关心名称/详情，在库存上下文只关心 SKU/数量。

### 18. 实体 vs 值对象 怎么选？⭐⭐⭐
💡 **问自己**："两个对象所有属性都一样，它们是同一个东西吗？"——**是**→ 实体（有唯一 ID、`equals` 只看 ID、属性可变，如两个人身份证号不同就是两个人）；**无所谓/可以互换**→ 值对象（无 ID、`equals` 看属性、**不可变 final**、如两张 100 元钞票谁都一样💴）。典型值对象：Money、Address。

### 19. 聚合设计三原则（必背）⭐⭐⭐
💡 ① **一致性边界内**的对象才放一个聚合（强一致的最小单元）；② 聚合要**尽量小**！跨聚合的一致性用**最终一致**（领域事件）解决；③ 外部只引用**聚合根 ID**，不引用聚合内部对象。本质：**聚合根是唯一入口，修改聚合内部必须通过聚合根方法**。

### 20. 防腐层（ACL）是什么？⭐⭐
💡 在两个上下文之间加一个**翻译官**，外部系统怎么变都不污染自己的模型。经典场景：库存系统要调第三方 ERP 的库存接口 → 写一个 `ThirdPartyInventoryAdapter implements InventoryPort`，把第三方奇怪的 DTO 翻译成自己上下文的领域模型🛡️。外部 ERP 升级改字段了，你只改 Adapter 一处。

### 21. 领域服务 vs 应用服务 怎么区分？⭐⭐⭐
💡 **领域服务**：**纯业务逻辑**，当一段逻辑**不属于任何单个实体/值对象**时用（如转账涉及两个 Account 聚合）→ **不碰数据库、不管事务、无状态**🏢；**应用服务**：**流程编排的薄层**，调仓储、管事务、组装值对象 → **几乎不含业务规则**🙋。口诀：**领域服务管"算"，应用服务管"串"**。

### 22. 领域事件命名规则 + 两种传播姿势？⭐⭐⭐
💡 命名必须用**过去式**✏️：`OrderPlacedEvent`（订单**已**下单），而不是 `PlaceOrderEvent`。两种传播：**进程内事件**（Spring Event）→ 强一致/同事务，同一上下文内部解耦；**消息队列**（Rabbit/Kafka）→ 最终一致，跨上下文/跨服务。

### 23. Repository 应该给每张表建一个吗？⭐⭐⭐
💡 **绝对不能！** Repository **只面向聚合根**，不会有 `OrderItemRepository`——因为 OrderItem 只能跟着 Order 聚合根一起存取（一致性由聚合根保证）。仓储接口定义在**领域层**，实现放**基础设施层**（依赖倒置，MySQL 换 PostgreSQL 领域层一行不动）。

### 24. DDD 四层分层架构是哪四层？⭐⭐
💡 **用户界面层**（Controller、DTO，接请求转格式）→ **应用层**（ApplicationService，流程编排 + 事务注解，**很薄**）→ **领域层**（核心！实体/值对象/聚合/领域服务/领域事件/Repository 接口，**纯净无技术依赖**💎）→ **基础设施层**（Repository 实现、MQ、缓存、第三方 SDK，实现领域层接口）。口诀：**界面→应用→领域→基建，依赖倒置、领域层是宝石👑**。

# 三、Docker 容器技术（12 题）

### 25. 容器 vs 虚拟机 本质差异？⭐⭐⭐
💡 **虚拟化级别不同**：虚拟机（🐘）= **整台虚拟电脑**，自带 Guest OS（GB 级启动分钟级）；容器（🐣）= **进程级虚拟化**，**共享宿主机内核**（MB 级秒级启动、性能接近原生）。理解：Docker 容器本质是宿主机上的一个被隔离 + 限资源的普通进程。

### 26. Docker 底层三板斧是什么？⭐⭐⭐
💡 **Namespace 命名空间**（隔离视图：让每个容器有自己的 PID/网络/文件系统/用户）— 每人一个独立单间🚪；**Cgroups 控制组**（限制 CPU/内存使用上限）— 房间限电限水⚡；**UnionFS 联合文件系统**（镜像分层叠加、读写分离）— 透明描图纸叠画📄。三者组合 = 容器隔离 + 限资源 + 镜像分层的地基。

### 27. 镜像分层的好处 + 构建缓存原则？⭐⭐⭐
💡 三大好处：① **层只读 + 共享**（10 个容器用同一个镜像，磁盘只存一份！）；② **构建缓存**（层没变就直接跳过）；③ **Copy-on-Write**（容器改文件才复制到自己的可写层，互不干扰）。缓存原则：**变得少的写前面，变得勤的写后面**。

### 28. CMD vs ENTRYPOINT 必考题？⭐⭐⭐
💡 **CMD** = 默认参数/命令，`docker run 镜像 参数` 时**参数整体替换 CMD**；**ENTRYPOINT** = 固定入口，参数**追加到 ENTRYPOINT 后面**。经典组合：`ENTRYPOINT ["java","-jar","app.jar"]` 固定程序 + `CMD ["--spring.profiles.active=prod"]` 默认参数 → `docker run myapp --spring.profiles.active=test` 轻松切环境✨。

### 29. 持久化三种挂载怎么选？⭐⭐⭐
💡 **Volume 卷**（`-v myvol:/data`）：Docker 自管（/var/lib/docker/volumes），**推荐⭐正式环境**（DB 数据用这个）；**Bind Mount 绑定挂载**（`-v /宿主机路径:/data`）：开发时挂代码热更新；**tmpfs**（`--tmpfs /tmp`）：内存里，临时敏感数据。口诀：**正式用 Volume、开发用 Bind、敏感临时用 tmpfs**。

### 30. Docker 默认 bridge 为什么容器不能靠容器名互访？⭐⭐⭐
💡 默认 bridge 网络**没有内置 DNS**，容器之间**只能靠 IP** 访问（IP 还会变）。解决：**建自定义网络** `docker network create app-net` + `--network app-net` 加入 → **自带 DNS，容器名即域名🎯**！Spring Boot 里直接 `jdbc:mysql://mysql:3306/app` 就能连上。

### 31. 镜像瘦身三件套？⭐⭐⭐
💡 ① **多阶段构建**（编译和运行分开）；② **基础镜像换 JRE alpine**（JDK ~640MB → JRE alpine ~170MB）；③ 清理：`RUN` 里 `apt-get clean` / apk `--no-cache` 不保留缓存层；配合 `.dockerignore` 排除 target/、.git/ 无用文件。

### 32. Compose 的 depends_on 能保证服务先后吗？⭐⭐⭐
💡 **不能！** `depends_on` 只保证**启动顺序**（先起依赖的容器），但不保证**就绪**（MySQL 容器进程起来了但初始化还没跑完）。正确姿势：配合**健康检查** `depends_on: { mysql: { condition: service_healthy } }`，被依赖的服务健康检查过了才起当前服务。

### 33. Compose 一键起全家桶的完整姿势？⭐⭐
💡 四要素：`services:` 定义每个服务；`depends_on:` + `condition: service_healthy` 保证就绪顺序；`volumes:` 卷持久化（MySQL 数据不丢）；`networks:` 自定义网络让容器能靠名字互访。常用命令：`docker compose up -d`（后台起）、`docker compose ps / logs -f app / down`（停删）。

### 34. 容器启动就退出常见原因？⭐⭐
💡 Docker 容器跑完**前台主进程就会退出**。常见原因：① 主进程启动完自动退出（非守护化、没阻塞等待）；② 应用报错崩了（`docker logs 容器名` 看日志）；③ 端口映射/环境变量没配对。Java 必配：`ENTRYPOINT ["sh","-c","java -jar app.jar"]`，用 sh 做 PID 1 能正确处理信号。

### 35. 为什么容器推荐非 root 用户运行？⭐⭐
💡 默认 root 运行存在**安全扫描告警**——容器逃逸漏洞一旦被利用，攻击者直接获得宿主机 root 权限。标准姿势：Dockerfile 里 `RUN addgroup -S app && adduser -S app -G app` + `USER app` 切换用户运行。

### 36. sendfile / 零拷贝在 Docker 里怎么体现？⭐⭐⭐
💡 **sendfile** = 磁盘文件从页缓存直达网卡，**完全不经用户态**（传统路径 4 次拷贝 → 2 次）。Docker 镜像拉取时大量用 sendfile 传层，Nginx 静态文件服务 `sendfile on` 也是。本质：**应用层零拷贝 = 避免程序内数据复制**，OS 层 sendfile = 绕过用户态。

# 四、Dubbo 高性能 RPC（12 题）

### 37. Dubbo 是什么？RPC vs HTTP/REST 核心差异？⭐⭐⭐
💡 **Apache 顶级开源的高性能 Java RPC 框架**，让你**像调本地方法一样调远程服务**🔗。RPC（Dubbo/gRPC）vs HTTP/REST（Feign/HttpClient）：RPC **TCP 长连接 + 二进制序列化（快、爽但抓包麻烦）**；HTTP **文本 JSON（通用可读但慢一点）**。口诀：**内部选 RPC（快），对外选 HTTP（通）**，很多公司"对外 RESTful 网关 + 对内 RPC 通信"组合拳。

### 38. Dubbo 架构五角色 + 注册中心关键设计？⭐⭐⭐
💡 **Provider 提供者（暴露服务）、Consumer 消费者（调用方）、Registry 注册中心（Nacos/ZK，存"谁提供什么服务"的电话簿）、Monitor 监控中心（统计调用量耗时）、Container 容器（Spring 启动载体）**。关键设计：**注册中心只递电话簿，实际调用是消费者直连提供者**（点对点长连接）→ 注册中心短暂宕机，已建立的调用不慌🛡️。

### 39. Dubbo 负载均衡五种策略，怎么选？⭐⭐⭐
💡 **random 随机（默认⭐，按权重，通用场景）**、**roundrobin 轮询（实例配置相近）**、**leastactive 最少活跃（能者多劳，实例性能参差✅）**、**consistenthash 一致性哈希（同参数总打同一台，有状态场景/缓存命中）**、**shortestresponse 最短响应（对延迟敏感）**。提供者侧 `@DubboService(weight=300)` 可配权重。

### 40. 集群容错六种模式，怎么选？写操作为什么用 failfast？⭐⭐⭐
💡 **failover（默认⭐故障转移）**：失败换一台重试 → **读操作**；**failfast（快速失败）**：只调一次失败立刻报错 → **非幂等写操作（下单/支付！）**；**failsafe**：失败忽略只记日志（不重要如审计）；**failback**：定时偷偷重发（消息通知）；**forking**：并行调 N 台谁快用谁（实时性要求极高）；**broadcast**：广播所有实例逐个调（刷新缓存）。⚠️ **写操作用 failfast 的核心：重试会导致重复下单💸，幂等性必须自己保证**。

### 41. 超时配置优先级 + 超时设太短的危害？⭐⭐⭐
💡 优先级（从高到低）：**方法级 @Method > 接口级 @DubboReference > 接口级 @DubboService > 全局配置**。超时**必须 ≥ 提供者实际 P99 耗时**！不然提供者还在苦干、消费者已判"死刑" + 触发重试 → **重试风暴雪崩放大器😱**。慢接口（报表导出）单独放宽到 60s 是正确姿势。

### 42. Mock 降级三种姿势？⭐⭐
💡 **简单 mock**：`@DubboReference(mock="return default")` 调不通返回默认值 / `force:return null`（强制不调真服务，压测用）；**自定义 Mock 类**：实现接口 + 返回兜底数据（`mock="true"` 自动按接口名 + "Mock" 找类）；配合 Sentinel 降级更灵活。核心：**给用户一个台阶，别让用户看 500 裸异常🛝**。

### 43. Dubbo / Triple / gRPC / REST 四种协议怎么选？⭐⭐⭐
💡 **dubbo**：单一长连接、NIO 异步，**经典默认，小数据高并发王者**⚡；**triple（Dubbo 3 主推⭐）**：基于 **HTTP/2 + 兼容 gRPC + 支持流式调用**，云原生时代新宠（穿越网关无压力）；**gRPC**：Google 出品，跨语言超强；**rest**：HTTP 风格方便调试跨语言。**新项目建议 triple**。

### 44. 序列化方式性能排序 + 怎么选？⭐⭐⭐
💡 性能排序：**protobuf > hessian2 / fastjson2 >> HTTP+JSON**；体积：protobuf 最小。选型口诀：**跨语言选 Protobuf**、**Java 内部选 hessian2（Dubbo 默认）或 fastjson2**、**需要可读调试选 JSON**。**Java 原生序列化别用**（慢、大、还有反序列化漏洞）。

### 45. Dubbo 3 应用级服务发现 vs 老版本接口级？⭐⭐⭐
💡 老版本按**接口**注册 —— 万级接口注册中心扛不住💥；Dubbo 3 改成按**应用**注册 —— **注册中心数据量暴降 90%**。外加新特性：**Triple 协议（HTTP/2 + gRPC 兼容）、与 K8s/Service Mesh 云原生深度融合、多语言生态（Java/Go/Rust/Node.js）**。

### 46. Dubbo vs Spring Cloud 怎么选？⭐⭐⭐
💡 **Dubbo**：定位"RPC 框架 + 轻量治理"，**长连接二进制性能强**、国内生态中文好；**Spring Cloud**：定位"微服务全家桶"（网关/配置/总线/熔断全套生态大礼包），HTTP REST 直观但性能稍逊。**现在主流组合：Spring Cloud Alibaba + Dubbo** —— 用 Spring Cloud 的生态（Nacos/Sentinel），内部通信用 Dubbo 的高性能 RPC，鱼和熊掌兼得🐟🥂。

### 47. Dubbo 常见坑排雷表？⭐⭐⭐
💡 ① **写操作用默认 failover** → 重试导致**重复下单💸**（改成 failfast + retries=0）；② **消费者超时设太短** → 重试风暴雪崩放大器；③ **DTO 没实现 Serializable**（用 hessian 时也要保留）；④ **大对象传输** → 网络拥塞超时（精简 DTO，大文件走 COS 外链）；⑤ **循环依赖 A↔B** → 维护噩梦（拆分服务单向依赖）。

### 48. Dubbo 注解四件套速记？⭐⭐
💡 `@EnableDubbo`（启动类，开启 Dubbo 能力）→ `@DubboService`（提供者实现类，暴露远程服务，可配 version/group/weight）→ `@DubboReference`（消费者字段，注入远程服务代理，可配 timeout/retries/loadbalance/cluster/mock）→ `@Method`（Reference 里面方法级精细控制）。

# 五、Kubernetes 容器编排（12 题）

### 49. K8s 是什么？Docker 和 K8s 的关系？⭐⭐⭐
💡 **K8s = 容器编排平台**，帮你自动部署、扩缩容、自愈、管理**几百上千个容器**。口诀：**Docker 负责"生"（单机打包运行），K8s 负责"养"（集群调度治理）**🎫——Docker 是基础，K8s 管的就是它。

### 50. K8s 集群的大脑 + 四肢各是什么？⭐⭐⭐
💡 **Control Plane 控制平面（大脑🧠）**：**API Server**（唯一入口）+ **etcd**（集群数据库📦）+ **Scheduler**（调度员📅给 Pod 挑节点）+ **Controller Manager**（各种控制循环：期望 vs 实际，不符就纠偏 🎮）。**Node 工作节点（四肢🖥️）**：每个 Node 有 **kubelet（节点管家👷）**+ **kube-proxy（网络转发🔀）**+ 容器运行时。

### 51. 一条 `kubectl apply deployment.yaml` 后发生了什么？⭐⭐⭐
💡 七步：① `kubectl` → **API Server** 写 etcd（"我要 3 个 Pod"）；② **Deployment 控制器**发现期望 3、实际 0 → 创建无节点 Pod；③ **Scheduler** 看到无家 Pod，算分挑节点"Node-1 最闲"；④ API Server 写 etcd 绑定 Pod → Node-1；⑤ **Node-1 的 kubelet** 看到"我的"新 Pod → 拉镜像、创建容器；⑥ 跑起来上报 **Running**；⑦ Controller 发现期望 3 实际 3 → 完成。**全声明式：只说"我要多少"，系统自己让实际追期望**✨。

### 52. Pod / Deployment / Service 三者关系？⭐⭐⭐
💡 **Pod** = 最小调度单元（1+ 容器，**朝生暮死、IP 会变**）；**Deployment** = **副本管家**，保持副本数 + 滚动更新 + 回滚（不直接管 Pod，管中间层 **ReplicaSet**，层层负责）；**Service** = **稳定的门牌号📇**——给一组 Pod 提供固定虚拟 IP + 负载均衡 + 服务发现，Pod IP 变了 Service 自动更新。

### 53. Service 四种类型各什么用？⭐⭐⭐
💡 **ClusterIP（默认）**：集群内部虚拟 IP，只集群内可访问 → 微服务互调⭐；**NodePort**：每台节点开 30000-32767 区间端口，外部 IP:端口可访问 → 测试/演示；**LoadBalancer**：云厂商分配公网负载均衡 → 生产上云；**ExternalName**：DNS 别名到外部服务 → 引用外部 API。集群内访问 Service 用域名：`服务名.命名空间.svc.cluster.local`（同命名空间直接 `http://java-app`）。

### 54. livenessProbe / readinessProbe / startupProbe 三种探针区别？⭐⭐⭐
💡 **liveness 存活**：判断"还活着吗"→ 失败**杀掉重启**容器💓；**readiness 就绪**：判断"能接客了吗"→ 失败**摘除流量不重启**🍽️；**startup 启动**：给慢启动应用（JVM 20-60s）**保护期**——通过前不做前两种检查🔥。Java 必须配 startupProbe 或延长 initialDelay，不然探针太急陷入 **CrashLoopBackOff 死循环**。配合 Spring Actuator 暴露 `/actuator/health/liveness` 和 `/readiness`。

### 55. 滚动更新怎么做到不停机发布？⭐⭐⭐
💡 六步循环：① 起一个**新版本 Pod** → ② 等就绪探针通过 → ③ **Service 自动把流量切给它** → ④ **杀一个旧 Pod** → ⑤ 还有旧 Pod 继续循环 → ⑥ 全量替换完成✅。新版本有问题？`kubectl rollout undo deployment/xxx` **一键回滚**⚡。发布进度：`kubectl rollout status deployment/java-app`。

### 56. HPA 自动弹性伸缩怎么配置？前提条件？⭐⭐⭐
💡 YAML 定义 target（Deployment）+ min/maxReplicas + metrics（CPU 利用率超 70% 就扩容）。**前提二**：Pod 必须配了 `resources.requests`（HPA 按它算百分比）+ 集群装了 **metrics-server**。大促流量一来自动加 Pod，深夜低谷自动缩 → **省下的都是真金白银💰**。

### 57. Pod 常见异常状态怎么排查？⭐⭐⭐
💡 **Pending**（没节点收留）：`kubectl describe pod` 看 Events → 资源不够/调度约束；**ImagePullBackOff**（镜像拉不下）：tag 写错/私有仓库未认证 → 核对镜像名 + 配 imagePullSecrets；**CrashLoopBackOff**（起来就崩反复重启）：`kubectl logs --previous` 看崩溃前日志 → 应用异常/探针误杀/OOM；**OOMKilled**（内存超限被杀）：调大 memory limit。排错三板斧🥇describe 看 Events + 🥈logs 看日志 + 🥉exec 钻进容器。

### 58. ConfigMap vs Secret 区别 + 怎么注入？⭐⭐
💡 **ConfigMap**：存明文配置（端口/开关）；**Secret**：存敏感数据（密码/token/证书），**Base64 编码（⚠️不是加密！只是不裸奔）**。两种注入：① **环境变量** `valueFrom.configMapKeyRef`（Spring Boot 天然支持环境变量覆盖配置，`SERVER_PORT` 覆盖 `server.port`）；② **挂载文件**（ConfigMap 修改后 Pod 内热更新生效！）。

### 59. 声明式 vs 命令式的本质差别？⭐⭐
💡 **命令式**（`kubectl run xxx`）：一步步告诉它"怎么做"（过程导向），不可重放、难审计；**声明式**（`kubectl apply -f xxx.yaml`）：**只说"我要什么"**（结果导向），K8s 控制器自动让集群追上去，YAML 进 Git 可审计可回滚。**生产一律声明式**。

### 60. Java 应用上 K8s 四个必配项？⭐⭐⭐
💡 ① **startupProbe / 延长 initialDelay** 兼容 JVM 慢启动，防 CrashLoopBackOff；② **resources.requests/limits** 合理限额（requests=调度依据，limits=天花板）；③ **Spring Actuator + 探针** `/actuator/health/liveness` + `/readiness`；④ **优雅停机** `terminationGracePeriodSeconds`，让 Pod 摘除流量后把正在处理的请求做完再退出。

### 61. K8s 为什么声明"容器只有一个主进程"？⭐⭐⭐
💡 因为探针判断死活的依据就是**主进程 PID 1**（主进程没了 = 容器死了 → 重启）。如果主进程 `sh -c "java -jar app.jar"` 里 java 崩了但 sh 还活着，容器就不会重启 → 假死。正确姿势：直接 `ENTRYPOINT ["java","-jar","app.jar"]` 让 java 当 PID 1。

### 62. PV / PVC 是什么？怎么配对？⭐⭐
💡 **PV 物理存储**（集群里的"充电宝"，预先建好的持久化存储池）+ **PVC 存储申请单**（应用写"我要 10Gi 存储、ReadWriteOnce"）→ K8s **自动配对**最合适的 PV 给 PVC。类比充电宝租借：你只管写 PVC 申请单要多少毫安🔋，K8s 帮你找库存匹配、把"充电宝"挂到 Pod 的 `/var/lib/mysql`。

# 六、Nginx 高性能 Web 服务器（12 题）

### 63. Nginx 为什么这么快？架构模型 + 底层原理？⭐⭐⭐
💡 **Master-Worker 模型**：1 个 Master（读配置、管 Worker 生死）+ N 个 Worker（= CPU 核数，是真正干活的打工人👷）。每个 Worker 用 **epoll 事件循环**（Linux 高效事件通知机制）+ **异步非阻塞**——一个 Worker 就能同时盯**几万连接**（谁就绪处理谁🌀，不像一连接一线程那样雇几万服务员，先破产😱）。

### 64. location 匹配优先级口诀？⭐⭐⭐
💡 **`=`精确 > `^~`前缀（命中后跳过重则）> `~`/`~*`正则（按书写顺序谁先命中谁赢）> 普通前缀（最长优先）> `/`兜底**。记忆口诀：**先等号，再^~，正则抢着配，普通比长短，最后兜底/**。

### 65. root vs alias 经典易混点怎么区分？⭐⭐⭐
💡 **root 是拼接**：`location /img/ { root /data; }` + 访问 `/img/a.png` → **`/data/img/a.png`**；**alias 是替换**：`location /img/ { alias /data/; }` + 访问 `/img/a.png` → **`/data/a.png`**（alias 的 `/img/` 被 `/data/` 替换掉了）。防呆：alias 结尾必须带 `/`、只能用在 location 里、root 可以全级别用。

### 66. 正向代理 vs 反向代理 怎么一句话分清？⭐⭐⭐
💡 **代理谁**：**正向代理**🧑‍🤝‍🧑 = 代理**客户端**（客户端知道代理存在，服务器不知道——翻墙/公司上网管控）；**反向代理**🏢 = 代理**服务器**（客户端知道代理存在（域名），但不知道后端真有几台服务器在干——负载均衡/隐藏后端/网关）。类比：正向 = 帮你跑腿代买奶茶的小哥🧋；反向 = 你只管点单，奶茶店后厨换了几个人你不知道🍳。

### 67. proxy_pass 末尾 `/` 到底有什么坑？⭐⭐⭐
💡 **带 `/` = 替换**：`location /api/` + `proxy_pass http://backend/` → 请求 `/api/user` 实际转发到 **`http://backend/user`**（`/api` 被替换掉了）；**不带 = 原样拼接**：`proxy_pass http://backend` → `/api/user` 转发到 **`http://backend/api/user`**。这是 Nginx 配置最经典的易混点之一⚠️。

### 68. Nginx 负载均衡五种策略？Java 场景怎么选？⭐⭐⭐
💡 **轮询**（默认，一人一个排队来，后端配置相近）→ **权重**（`weight=n` 按比例分，机器有强有弱）→ **ip_hash**（同 IP 永远打同一台，老用来解 Session 问题但现在用 Redis/JWT 啦）→ **least_conn**（谁手上活少给谁，请求耗时差异大）→ fair（第三方模块按响应速度）。Java 前后端分离无状态 + JWT → **默认轮询就很好**。

### 69. 前端 history 路由刷新 404 为什么？Nginx 怎么解决？⭐⭐⭐
💡 Vue/React 的 history 模式下，用户刷新 `/user/123`（浏览器地址栏）→ Nginx 按磁盘路径找 `/usr/share/nginx/html/user/123` → **找不到直接 404**💥（因为那是前端路由虚拟路径）。解法：`try_files $uri $uri/ /index.html;`（在 location / 里）→ 找不到的统统回退到 `index.html` 交给前端路由处理。

### 70. WebSocket 代理三大坑是什么？⭐⭐⭐
💡 ① 必须加 **`proxy_http_version 1.1` + `proxy_set_header Upgrade $http_upgrade` + `proxy_set_header Connection $connection_upgrade`**（不加这三行 WebSocket 秒断⚠️）；② **`proxy_read_timeout` 默认 60s太短**，长连接场景要改成 `3600s` 甚至更大；③ 用 `map $http_upgrade $connection_upgrade { default upgrade; '' close; }` 处理不是 WebSocket 的请求正常关闭。

### 71. 502 Bad Gateway 和 504 Gateway Timeout 什么区别？⭐⭐⭐
💡 **502 = 连不上后端**：Java 进程没起、端口配错、防火墙挡了 → `curl 127.0.0.1:后端端口` 先测后端；**504 = 连上了但响应超时**：Java 接口慢 SQL 等太久没回 → 看 access_log 的 `$upstream_response_time`（后端耗时），调 `proxy_read_timeout` 或优化后端接口。口诀：**502 是"没服务员"，504 是"服务员太忙了"**。

### 72. nginx -s reload 为什么能不断服务重载配置？⭐⭐⭐
💡 五步：① Master 校验新配置语法 → 语法错**直接放弃重载、老 Worker 继续工作**（稳！）；② 语法 OK 加载新配置；③ **启动新 Worker**（带着新配置开始接请求）；④ **通知老 Worker**：处理完手头现有请求就退休（优雅退出）；⑤ 全程没有一个 Worker 被杀，服务完全不断⚡。

### 73. Nginx 性能优化清单（Java 运维必会）？⭐⭐
💡 八条：① `worker_processes auto`（Worker = CPU 核数）；② `worker_connections 10240`（并调系统 `ulimit -n`）；③ `sendfile on`（静态文件零拷贝）；④ `gzip on` + `gzip_comp_level 6`（压缩省带宽）；⑤ 静态资源 `access_log off`（少磁盘 IO）；⑥ 后端 upstream 配 `keepalive 32`（到后端也复用连接）；⑦ `proxy_cache` 给热点接口缓存；⑧ 先压测 `ab/wrk/jmeter` 再调优，别拍脑袋。

### 74. Nginx 三大动静分离 / 跨域 / 限流 怎么搞？⭐⭐⭐
💡 **动静分离**：`location /api/` → proxy_pass 给 Java，`location /static/` → 本地文件直接吐，Java 线程全部省下来跑业务；**跨域**：**最优雅方案是 Nginx 反向代理让前后端同源**（前端 `https://www.example.com/`，API `https://www.example.com/api/`），根本不跨域；**限流防刷**：`limit_req_zone` 按 IP 限速 `rate=10r/s burst=20 nodelay`，超限返回 429。

# 七、RPC 远程过程调用（10 题）

### 75. RPC 一次调用的五大核心步骤口诀？⭐⭐⭐
💡 **一代理、二序列化、三传输、四反射、五回填**🎵。对应：① **动态代理**（JDK 代理 / ByteBuddy 拦截接口调用，伪装成"本地方法"）；② **序列化**（对象 → 字节流才能上网传输）；③ **网络传输**（Socket / **Netty** NIO 异步发送）；④ **反射调用**（服务端按类名+方法名找到实现类并执行）；⑤ **结果回传反序列化**。

### 76. JDK 动态代理 原理一句话？⭐⭐⭐
💡 `Proxy.newProxyInstance` **在运行时动态生成一个实现了目标接口的代理类**（叫 `$Proxy0`）→ 这个代理类的**所有方法都转发到 `InvocationHandler.invoke()`**里 → 我们就在 invoke 里"偷梁换柱"发网络请求。关键点：**必须有接口**，没接口就得用 ByteBuddy / CGLIB 字节码增强（Dubbo 默认用 Javassist）。

### 77. 序列化选型怎么挑？⭐⭐⭐
💡 性能排序：**protobuf > hessian2 / fastjson2 >> HTTP+JSON**；体积：protobuf 最小；**跨语言**：gRPC 用 protobuf（天然跨 10+ 语言）→ 跨语言选 protobuf；**Java 内部**：Dubbo 默认 hessian2，国内很多用 kryo（超快但 Java 专属）；**需要可读调试**：JSON。**Java 原生序列化别用**（慢、大、反序列化漏洞）。值对象记得留**无参构造器**（hessian 要求）。

### 78. TCP 粘包拆包是什么？RPC 框架怎么解？⭐⭐⭐
💡 TCP 是**字节流、没有消息边界**——两条消息可能粘成一坨（Nagle 合并、缓冲等待），也可能被拆成几段（MSS 分段）。RPC 框架解法（**四种，业界通用**）：① **定长帧**；② **特殊分隔符**；③ **长度字段（最通用、工业标准⭐）**——报文头写 body 长度，双方按长度读；④ 自定义协议（Dubbo 16 字节定长消息头里就包含 body 长度）。Netty 里直接用 `LengthFieldBasedFrameDecoder`。

### 79. gRPC 为什么能这么火？核心三件套 + 四种流模式？⭐⭐⭐
💡 三件套：**Proto IDL 文件**（接口描述语言，跨语言共享契约）+ **protoc 代码生成器**（自动编译出各语言客户端/服务端骨架）+ **HTTP/2 + Protobuf**（二进制多路复用、性能拉满⚡）。四种流模式：**一元调用**（一问一答，最普通）、**服务端流**（一问多答，推送下载）、**客户端流**（多问一答，批量上传）、**双向流**（两边随便说，聊天/实时同步）。

### 80. 手写迷你 RPC 框架（100 行那种）骨架是什么？⭐⭐⭐
💡 **Rocket 🚀 版：三文件 + 两类**：服务端（RpcServer）开 ServerSocket accept → 等连接后 ObjectInputStream 反序列化 RpcRequest → **反射 invoke 目标方法** → ObjectOutputStream 写回 RpcResponse；客户端（RpcClient）用 **Proxy.newProxyInstance** 在 InvocationHandler 里把"接口名+方法名+参数"打包成 RpcRequest → Socket 发给 Server → 等结果回。和 Dubbo 的差距？Dubbo 把 BIO 换成 **Netty NIO**、Java 序列化换 **Hessian/Protobuf**、加 **注册中心/负载均衡/集群容错**，骨架一模一样。

### 81. Dubbo 里的服务挂了怎么处理？心跳+超时+熔断三层？⭐⭐⭐
💡 **三层兜底**：第一层 **心跳检测**（连接层心跳 / 注册中心心跳）→ 节点挂了自动从消费者列表摘除；第二层 **超时快速失败 + failover 重试其他节点**（不会一直卡着）；第三层 **熔断降级兜底**（下游全挂 → mock 返回默认值 / throws BizException("服务繁忙，请稍后")）。三层叠起来就是"Sentinel 之前" Dubbo 内置的容错体系。

### 82. RPC 和 HTTP 到底是什么关系？为什么 gRPC 又在 HTTP/2 上跑？⭐⭐⭐
💡 **RPC 是"调用方式的思想"**（让调用远程服务像调本地方法一样简单，技术选型自由），**HTTP 是"传输协议"**（规定报文格式和交互方式）。所以 RPC 可以跑在** TCP 私有协议**上（老式 Dubbo）、也可以跑在** HTTP/2** 上（gRPC / Dubbo Triple）。gRPC 选 HTTP/2 是因为它有**多路复用（一个连接并发多请求）、头部压缩、二进制帧**——性能好 + 能穿越网关/防火墙（网关天然认识 HTTP）。口诀：**RPC 是外卖 App，HTTP/2 是外卖 App 用的交通网络**🚗。
